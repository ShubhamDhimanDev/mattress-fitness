# Shopify data model (proposed)

Status: **proposal, 2026-10-11.** Names, types and limits must be verified on a development store in Phase 0 (V-04, V-05) and finalised in P3A-02. The definitions are created by `scripts/shopify/apply-definitions.mjs` from one JSON spec so the development and client stores are identical. All metafield and metaobject definitions that the storefront reads must have **Storefront API access** enabled _(verify)_.

Principles: one product per mattress model with one variant per size (SOW §8); store attributes once, on the product; let rules and filters read them so new products behave correctly without code; keep client-editable text in Shopify admin.

### Homepage sections and promo tiles (as encoded in `scripts/shopify/definitions.json`)

`homepage_section.type` is a single-line text field limited to a fixed list of choices. The storefront code lists the same values (`HOMEPAGE_SECTION_TYPES`) and a test keeps the two in step.

| `type` value                                       | Content it uses                             | Behaviour                                                                             |
| -------------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------- |
| `hero`, `promo-banner`, `financing`                | heading, body, image, link and `link_label` | Shows the content entered in admin                                                    |
| `shop-by-size`, `featured`, `brands`, `categories` | heading, order and enabled only             | Fills itself from the catalog; body, image and link are not used                      |
| `signup`                                           | none yet                                    | Reserved for the email and text-message signup (P7-02); shows nothing until it exists |

- `link_label` is optional text for the button. Left empty, the heading itself becomes the link. It exists so a link never needs generic wording such as "Learn more" (added in P3B-13).
- `order`: smaller numbers appear first; entries without a whole number go last. A section shows only when `enabled` is on.
- `link` (here and on `promo_tile`, and `site_settings.promo_bar_link`) is plain text, a relative path or an https URL, because Shopify's `url` type rejects relative paths. The storefront validates it against an allow-list (T-08).
- `promo_tile.position`: 1 puts the tile first; 4 makes it the fourth cell, counting products and tiles together. A tile whose position is beyond the products shown is held back until "Load more" brings enough products. The tile's heading is shown on the tile and used as the link text; without a valid link the tile is shown but is not clickable. Tiles show only on the unfiltered, default-sorted first view of a collection (not under a filter, a different sort or a cursor), and a tile is never shown alone after the last product.
- `brand.slug` must equal the metaobject handle (see the table above). `custom.brand` on a product is a reference to a `brand` metaobject, and `vendor` is kept for filters.

Status: these facts are copied from `definitions.json`, which is checked against the Admin GraphQL 2026-10 reference but not yet applied to a development store (V-05).

The exact schema for `offer_rule` triggers is finalised in P3A-02 after V-05; keep rules declarative (data), not code.

### Store time zone, pickup location mapping, quiz scoring rules (as built 2026-10-26, not yet run against a store: V-05)

- **`store.time_zone`** (P3B-16) is optional, single-line text holding an IANA zone such as `America/Chicago`. `parseStoreRecord` accepts it (aliases `timezone`, `timeZone`) and drops an unrecognised name with a warning (`isValidTimeZone`, Intl). With a valid zone, store cards and store pages compute "Open now, closes ..." and today's hours in the **store's** time (`openStatus`, `todaysHours`; overnight hours belong to the day they start on). Without one the weekly hours are listed (`summarizeWeeklyHours`, "Mon-Fri: 10:00 AM - 9:00 PM; ...") and the table has no highlighted day, but nothing says open or closed: no zone is ever guessed. There is no store importer in `scripts/` yet (only the product importer), so the field is added to `definitions.json` and read by the storefront; the store list import is the CLR-015 sheet task.
- **`store.location_handle` to a Shopify location** (P3B-10, REQ-PDP-003). The Storefront API `Location` object has only `id`, `name`, `address` and (with token access) metafields: there is no handle. The storefront matches the field to the location's `name` (case, spaces and hyphens ignored) or, if the field is all digits, to the numeric part of the location's `gid`. `ProductVariant.storeAvailability(first, near, ...)` has **no** filter by location, so one request reads up to 250 pickup locations for the variant and the storefront picks the store's own (`StoreAvailability { available, pickUpTime, location { id name } }`, scope `unauthenticated_read_product_pickup_locations`; `quantityAvailable` is not requested). Cached 60 s (the availability strategy, DEC-024). UNVERIFIED(V-05): the scope on the client's token, that locations with zero stock appear with `available: false`, and the meaning of "available" for a location whose pickup is switched off.
- **`quiz_scoring_rule`** (P6-13, REQ-QZ-004, NFR-005). One rule per entry so the client edits in a form. The reader (`app/lib/shopify/quiz-data.ts`) reads `quiz_question` > `quiz_option` > `quiz_scoring_rule` in one nested query and rebuilds the loose JSON that `parseQuizConfig` already validates, so the parser stays the only judge of validity (a bad rule is dropped with a logged warning, never a crash). Per option: referenced rules win and the JSON `scoring_rules` field is ignored; with no references the JSON is used; never both. `budget` uses `value` as the maximum and `min_dollars` as the minimum; `size` uses `value`; an unknown `effect` is passed on as an unreadable `exclude` flag so the parser reports it. With no `quiz_question` entries, or a failed read, the built-in default quiz is used.

### What the storefront reads today (as built, 2026-10-15)

Definitions are in `scripts/shopify/definitions.json` and have not been applied to any store (V-05). Storefront code reads, through the Storefront API: the navigation menu named by `PUBLIC_NAV_MENU_HANDLE` (only when that setting is set; see "Navigation menu" above); `homepage_section`, `promo_tile` and `brand` metaobjects; three fields of the first `site_settings` entry (`promo_bar_text`, `promo_bar_link`, `support_phone`; `app/lib/shopify/site-settings.ts`); the product metafields `custom.comfort_level`, `mattress_type`, `sleep_positions`, `benefits`, `product_line`, `height_inches`, `specifications`, `features`, `brand`, `faqs` (also on collections), `extend_category` and the variant metafield `custom.dimensions`. Not read by any storefront query yet: `custom.delivery_type`, `related_foundations`, `related_protectors`, `related_bedding`, `compare_group` (the comparison page uses fixtures), and the `offer_rule` and `delivery_zone` metaobjects, and the other `site_settings` fields (`haul_away_max`, `financing_copy`, `extend_enabled`).

The product page's add-ons slot (foundations, bases and frames; `GET /api/product-addons`, ARCHITECTURE section 5a) reads its size-matched relations from the same `OFFER_CONFIG_JSON` (`matchingAddOns.foundations`), **not** from the `related_foundations` product field; only the add-ons' price and availability come from the Storefront API.

Until P4-12 the offer rules, the delivery zone, the free-delivery threshold and the haul-away maximum come from the server-only value `OFFER_CONFIG_JSON` (DEC-030; `storefront/app/lib/offers-runtime/config.ts`), not from `offer_rule`, `delivery_zone` or `site_settings`. Two differences from the table above matter when the metaobject reader replaces the seam: the seam holds the free-delivery number twice (`rules.freeDelivery.thresholdCents` for the cart message and `zone.freeOverCents` for the zone) and the haul-away maximum as `rules.haulAway.maxPieces`; and the zone's promise text is `inHome`, `parcel` and `pickup` in the seam, while the `delivery_zone` definition has `promise_white_glove` and `promise_parcel` only (no pickup promise field, and `fee_text` is not read by the code). Reconcile these field names in P4-12, with the client's approval where wording is client-facing. Stores are read from the `store` metaobjects when the store has at least one valid entry (`app/lib/shopify/store-data.ts`, long cache) and fall back to labelled fixtures otherwise; the quiz configuration reader (`app/lib/shopify/quiz-data.ts`) exists but the quiz routes do not pass it the Storefront client yet, so the quiz still runs on its built-in default; quiz products and comparison candidates are served from fixtures through `app/lib/pages/data-source.ts` (DEC-023) until P3B-01.

Cart attributes the storefront writes (names fixed in `app/lib/offers/attributes.ts`, they appear as order attributes in admin): `delivery_choice` (`in-home` or `pickup`), `offer_declined_comfort_guarantee`, `offer_declined_haul_away`, `offer_declined_protection` (`yes` or `no`). Coverage cart lines carry the line attributes `_extend_plan_id`, `_extend_covered_product_id`, `_extend_term` (our keys, see EXTEND.md). Whether cart attributes become `Order.customAttributes` is unverified (V-20).

### Navigation menu (REQ-NAV-002, as built 2026-10-23, not yet run against a store: V-05)

A Shopify navigation menu (**Online Store > Navigation**) can drive the header and the mega menu, but only when the deployment **opts in**: the setting `PUBLIC_NAV_MENU_HANDLE` names the menu's handle (for example `main-menu`). With it unset (or `none`, or not a handle) the storefront shows its fixed navigation and makes no menu request, so a store's default `main-menu` (often only Home and Catalog) never replaces the designed navigation by accident. The handle is the menu's URL name (lower-case letters, digits and hyphens); where Shopify admin shows it for a given menu is not confirmed, the developer reads it on the development store _(verify)_.

What the storefront reads for the chosen menu (`app/lib/shopify/menu-data.ts`, cached with the long strategy): up to three levels of items, each with `title`, `type` and `url`. How the levels become the header, and the limits (code: `app/lib/nav-menu.ts`):

| Menu level in Shopify           | In the header                                                                                                                                                             |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Top-level item                  | An item in the header row. With no sub-items it is a plain link; with sub-items it opens a mega-menu panel (and, if it has a link of its own, the label also links there) |
| Second level that has sub-items | A **group heading** in the panel (it links if it has a usable link of its own)                                                                                            |
| Second level without sub-items  | A plain link; all such links share one heading-less group, placed where the first one is                                                                                  |
| Third level                     | The links under a group heading                                                                                                                                           |

Limits: at most **8** top-level items, **8** groups per item and **12** links per group (extra entries are left out), labels cut at **60** characters, a repeated link in one group (or the same label and link at the top level) left out. Link rules: a collection, product, page, blog, article or policy entry becomes the matching page of this website from its handle; Home, Collections, Catalog (all products), Search and the customer account page map to fixed pages; a plain web address on this store's own domain or the website's own domain must point at a public section (`/collections`, `/products`, `/pages`, `/brands`, `/blogs`, `/stores`, `/quiz`, `/compare`, `/search`, `/policies`, or the home page); any other `https://` address opens as an external link; anything else (`javascript:`, plain `http://`, spaces, over 500 characters) leaves that entry without a link, and an entry with neither a link nor sub-items is left out. If nothing usable is left, or the read fails, the fixed navigation is shown. The sleep-quiz link is added after the menu unless the menu already links to the quiz. Edits show after the long cache window (about an hour; ADMIN_GUIDE section 6.6).

## Service and add-on products

On the **Basic** plan (ADR-0006, ADR-0009): the Extend coverage products are **price-point variants** named `Extend-Protection-Plan-<price>` (at most 250), published to the headless channel and kept out of collections and search; the haul-away product ("Recycle and disposal service") is a single variant whose quantity is the number of pieces; gift products are normal variants made free by automatic discounts.

Product tags the code relies on (conventions of ours, ASSUMPTION V-05, V-16: the Storefront `products(query:)` must return products hidden from search): `extend-coverage` on every Extend price-point product (the coverage catalog read, 250 variants at most, `app/lib/extend/coverage-catalog.ts`) and `offer-only` on any other service, gift or protector product; both keep the product out of the product sitemap and `noindex,follow` ([SEO_POLICY](SEO_POLICY.md)). The client team sets `offer-only` in admin (admin guide entry open). Which variants are gifts, protectors or the haul-away service is **not** read from tags or fields: it comes from the offer rules (variant ids), because a direct-API cart can attach any attribute to any line.

Haul-away ("Recycle and disposal service"), comfort-guarantee protectors per size, matching protectors, pillows, bedding, and the Extend coverage products (modelling per Q-005) are ordinary Shopify products, excluded from collections and search where appropriate, so they appear on orders as normal lines (SOW §5).
