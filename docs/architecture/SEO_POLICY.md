# SEO policy: canonical URLs, faceted URLs, robots and sitemap

Requirement REQ-SEO-001; task P7-04; decision DEC-044. Code: `storefront/app/lib/seo/` (pure, unit-tested), the routes `[robots.txt]`, `[sitemap.xml]`, `sitemap.$type.$page[.xml]`, `sitemap.extras[.xml]`, `entry.server.tsx` (Link header) and `collections.$handle.tsx` (tag). Status 2026-10-15: **built and verified on the dev server against a mock store; not verified on the real store or host.**

## Origin

Every absolute URL (canonical, sitemap, robots `Sitemap:` line, JSON-LD) uses `PUBLIC_SITE_URL` through `app/lib/site-origin.ts`. Development falls back to the request's own origin; elsewhere a missing value means **no canonical, no breadcrumb markup, a 404 for the sitemaps and no `Sitemap:` line**, never the Host header (P-L2). Set it before launch ([DEPLOYMENT](../deployment/DEPLOYMENT.md)).

## Canonical URL

One rule: **origin + path, no query string, no fragment, no trailing slash (except `/`)**. So these all share one canonical: `/collections/firm`, `/collections/firm?size=queen`, `/collections/firm?sort=price-asc&cursor=...`, `/products/x?Size=Queen` and any tracking parameters. It is sent two ways from the same helper (`canonicalUrl`):

- an HTTP `Link: <url>; rel="canonical"` header on every indexable `200` GET document (`entry.server.tsx`), which covers all templates at once;
- a `<link rel="canonical">` tag from the `meta` function of `collections.$handle.tsx`. Other templates (product, brand, page, store, blog) rely on the header until their owners add the tag with `canonicalMeta()`.

Never canonical (and never in the sitemap): `/cart`, `/account`, `/checkout-steps`, `/delivery`, `/api`, `/webhooks`, `/discount`, `/search`, `/compare`, `/sitemap*`, `/robots.txt`, `/_dev`. Matching ignores case and percent-encoding because routes do.

## Faceted URLs (decision)

Filters, sort and the load-more cursor live in the query string (`size`, `brand`, `product_type`, `comfort`, `mattress_type`, `benefit`, `position`, `product_line`, `price_min`, `price_max`, `sort`, `cursor`: `MANAGED_FILTER_PARAMS`). Policy:

1. The plain collection and brand pages are indexed and listed in the sitemap.
2. Any filtered, sorted or paginated view **canonicalises to the plain URL**. It is not `noindex`: a `noindex` combined with a canonical to another URL is a mixed signal, and a `noindex` cannot be seen on a URL that robots.txt blocks.
3. robots.txt also **blocks crawling** of every managed parameter (`Disallow: /*?size=` and `Disallow: /*&size=` and so on, generated from the codec so a new filter is covered automatically; the name must start right after `?` or `&`, so `resize=` is not caught), to save crawl budget on combinations that all point at the same page. Accepted trade-off: a blocked URL that other sites link to can appear in results without a snippet; the canonical cannot be read there. Nothing on our own pages links to a filtered URL as a crawlable `<a href>` target that matters for ranking, and the 400-product catalog is small.
4. Internal search results are `noindex,follow` and are **not** blocked in robots.txt (a `noindex` can only be read on a URL the crawler may fetch; blocking and `noindex` together contradict each other). There is no canonical. Search URLs that carry a filter or sort parameter are blocked by the facet rule above; that is harmless because they are duplicates of the same noindexed page.
5. Curated landing pages that should rank for a facet ("firm mattresses") are **collections** (Shopify collection or brand page), not filter URLs.
6. Revisit if the client wants a specific single-filter page indexed: it becomes a collection.

## robots.txt

Generated by `buildRobotsTxt`. Each path rule is segment-safe: robots rules are prefixes, so `/cart` alone would also block `/cartridge`; the rules are `Disallow: /cart$` (the path itself), `/cart/` (below it) and `/cart?` (with a query), checked by a matcher in the tests. Blocks for every crawler group: `/cart`, `/account`, `/checkout-steps`, `/delivery`, `/api`, `/webhooks`, `/discount`, `/quiz?` (quiz answers and results are query state; the bare `/quiz` stays open), and the facet parameters above. Shopify-default groups kept: `adsbot-google` (ignores `*`), `Nutch` (blocked entirely), `AhrefsBot`, `AhrefsSiteAudit`, `MJ12bot` (crawl delay 10) and `Pinterest` (1); each repeats the rules because a named group ignores `*`. Trust pages (`/policies/*`: returns, shipping, privacy, terms) are **indexed** and have a canonical: they answer shoppers' pre-purchase questions and were only blocked because Shopify's default theme robots file does so. Shopify's Storefront sitemap does not list shop policies, so `sitemap/extras.xml` lists them (see Sitemap). Ends with `Sitemap: <origin>/sitemap.xml`.

## Sitemap

`/sitemap.xml` is an index of Shopify's resource sitemaps (Hydrogen's `getSitemap`, up to 250 URLs per page, `lastmod` from Shopify) for **products, collections, pages, blogs and articles**, plus `/sitemap/extras.xml`:

- Metaobject sitemaps are **not** listed (no page exists for them) and there are **no locale alternates** (US English only, NFR-008; the template's `EN-CA`/`FR-CA` were removed).
- `extras.xml` lists `/` and `/collections`; `/brands` and every `/brands/<handle>` only from real `brand` metaobjects (the sample brands and a failed read list nothing). There are no store pages and no `/stores` entries (the store locator was removed 2026-10-28, DEC-141). The quiz and compare pages are not listed.
- **Shop policies** (`/policies/privacy-policy`, `shipping-policy`, `terms-of-service`, `refund-policy`) are listed only for policies the shop has written, from a small cached read (`app/lib/shopify/shop-policies.ts`, query `ShopPolicyHandles`, Storefront API 2026-04). The URL handle comes from a closed list keyed by the Shop field, never from the handle Shopify returns, and equals the list in `routes/policies.$handle.tsx` (a test pins both). The subscription policy is not queried: the route answers 404 for it. A failed read lists none and is logged (`catalog.shop_policies_read_failed`). Policies carry no `lastmod`. Not yet checked against a real store (V-05).
- Handles are validated and percent-encoded; an unusable handle becomes the home page URL rather than a broken one. Unknown sitemap types and page numbers outside 1 to 100 are 404 before Shopify is called.
- Cached for a day (`public, max-age=86400`). A request with a query string (`?x=1`) is redirected (301, relative) to the bare URL, so the cached object is keyed by the path alone and a query cannot reach Shopify again. A page with no items (`/sitemap/products/99.xml`) is a 404, not a sitemap that lists the home page.
- **Offer-only products are left out** of the product sitemap and their product pages are `noindex,follow` (security review K-L3): the Extend price-point products, the haul-away service, gift variants and comfort protectors must be published to the headless channel so the cart can hold them, which would otherwise make them crawlable. They are recognised by the Shopify product tag `extend-coverage` (the Extend price points) or `offer-only` (any other service, gift or protector; **the client team sets this tag in Shopify admin; add it to the admin guide**), read by `app/lib/shopify/offer-only.ts`. Shopify's own `seo.hidden` metafield is the preferred second control; whether the Storefront sitemap honours it, and whether the tag search returns products hidden from search, must be verified on the development store (V-05, V-16). A failed read lists everything and is logged (`catalog.offer_only_read_failed`).
- **Assumption (unverified):** article handles from Shopify's sitemap arrive as `blog-handle/article-handle` and are linked as `/blogs/blog-handle/article-handle`. The mock store has no articles; check on the development store (V-05).

## Structured data

Product (with Offer or AggregateOffer), BreadcrumbList, FAQPage and Brand are built from the same data the page shows. `tests/unit/seo/structured-data.test.ts` checks each against the schema.org and Google rich-result required fields on recorded and fixture data, that **no rating or review markup exists anywhere** (no review source yet, Q-011), that an empty brand is omitted, and that hostile text cannot end the script block. There is **no Organization builder**; it needs the client's legal name, logo and profile links (not in the data model yet), so it is blocked on client data (CLR). **No origin, no absolute-URL markup:** `buildBreadcrumbJsonLd` returns null without an origin (Google requires absolute item URLs), so the collection, product and brand routes emit no breadcrumb script then; `buildProductJsonLd` leaves out the product and offer `url` fields rather than emitting relative ones (price, currency and availability stay). There are no store pages and no LocalBusiness markup (removed 2026-10-28, DEC-141). **WebSite** markup with a `SearchAction` was tried and removed: Google retired the sitelinks search box in 2024, so it would be speculative markup. Add it back only if a consumer needs it, and then with the client's site name.

## Titles and descriptions

Each route sets its own title through `formatPageTitle`. Unique `description` meta exists on collections, products, brands (real data only) and the quiz; a page-by-page audit of titles and descriptions on real content waits for the development store (P3A-01) and belongs to the Phase 7 gate.
