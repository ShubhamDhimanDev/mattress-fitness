## Environment variables

To run locally against a demo store with none of the third-party variables set, use [DEMO_STORE_SETUP](DEMO_STORE_SETUP.md) (`node scripts/setup/demo-env.mjs`).

Names only; values stay in the hosting platform's secret store and in git-ignored local files (`.env`, `.env.*`; only `.env.example` is tracked). The lists below were cross-checked on 2026-10-15 and again on 2026-10-26 against [.env.example](../../.env.example), `storefront/env.d.ts` and a search of `storefront/app/` and `scripts/node-server/` for each name (a search by name only; no variable was set and nothing was run). `PUBLIC_` prefixed variables are exposed to browsers by Hydrogen's convention; everything else is server-only. Code reads variables from the request-context `env` only (ADR-0004). **Resolved 2026-10-26:** the root `.env.example` now names `TRUSTED_CLIENT_IP_HEADER` and `TRACKING_LINK_HOSTS` and the variables of reviews, Klaviyo, chat, financing and Extend branding (the 2026-10-23 "gap" note and the "reserved, read by no code" line for them were stale). `deploy/mattressfitness.env.example` (the VPS template) sets only the variables a first VPS deploy needs, including `TRUSTED_CLIENT_IP_HEADER`; it does not list the optional third-party variables, so copy names from the root `.env.example` when a feature is switched on.

## Node server settings (Option B, ADR-0011)

Applies only when the built storefront runs on our own Node server (`scripts/node-server/`, task P9-12, [ADR-0011](../decisions/ADR-0011-node-server-entry.md), status Proposed). These are **host settings**, not storefront settings: the storefront never reads them (it reads only the request-context env, ADR-0004), and they are not in `.env.example`. In the VPS plan they are set in the **systemd unit** (`Environment=` lines of `deploy/mattressfitness.service.example`), **not** in the environment file `/etc/mattressfitness/env`, which holds the storefront variables above. Source of truth for ranges: `scripts/node-server/config.mjs`.

| Setting               | Default                  | Allowed                                                           | Meaning                                                                                                                                                                                                                       |
| --------------------- | ------------------------ | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PORT`                | `3000`                   | whole number 1 to 65535                                           | Port the server listens on. nginx's upstream must equal it                                                                                                                                                                    |
| `BIND_HOST`           | `127.0.0.1`              | a literal IPv4 or IPv6 address, validated with Node's `net.isIP`  | Interface to listen on. Loopback so only the reverse proxy can reach the server. A host name (including `localhost`), an out-of-range address or a typo is refused, never read as "everywhere"                                 |
| `TRUST_PROXY`         | `false`                  | `true` or `false`                                                 | When `true` the scheme comes from the first `X-Forwarded-Proto` value (the app decides HSTS from it, behind TLS-terminating nginx). Safe only with loopback binding and a proxy that overwrites that header. **`true` together with a non-loopback `BIND_HOST` is refused at start** (`node_server.config_invalid` naming `TRUST_PROXY`) |
| `MAX_BODY_BYTES`      | `1048576` (1 MiB)        | 1024 to 52428800                                                  | Request-body cap; a larger body gets 413. Keep equal to nginx `client_max_body_size`                                                                                                                                          |
| `SHUTDOWN_TIMEOUT_MS` | `10000`                  | 0 to 120000                                                       | How long a stop (SIGTERM or SIGINT) waits for in-flight requests and background work                                                                                                                                          |
| `CACHE_MAX_ENTRIES`   | `500`                    | 1 to 100000                                                       | Size cap of the in-process stand-in for the Workers `caches` global (Hydrogen's query cache and webhook replay marks). Lost on restart. The template unit does not set it; the default applies                                  |
| `CACHE_MAX_BYTES`     | `67108864` (64 MiB)      | 1048576 to 1073741824                                             | Estimated size cap **per named cache** of the same stand-in; oldest write is evicted first. An entry larger than one eighth of the cap is not stored at all. The template unit sets it to the default                          |

A value outside its range, or a malformed one, makes the server **refuse to start** and log `node_server.config_invalid` naming the setting (never a value); it also refuses when `SESSION_SECRET`, `PUBLIC_STORE_DOMAIN`, `PUBLIC_STOREFRONT_API_TOKEN` or `PUBLIC_CHECKOUT_DOMAIN` is missing, or `SESSION_SECRET` is shorter than 32 characters. `NODE_ENV=production` is also set in the unit. A changed setting needs `sudo systemctl restart mattressfitness`.

**Starting it.** After `npm run build` in `storefront/`, the script `start:node` (`node ../scripts/node-server/server.mjs`, in `storefront/package.json`) starts the server on the build in `storefront/dist`. It reads the storefront variables from the process environment only; it does not load a `.env` file itself, so for a local run supply them with the shell or with Node's own flag, for example `node --env-file=<file> ../scripts/node-server/server.mjs` (as written in VPS_RUNBOOK section 15; not run by the author of this document). `GET /healthz` answers `{"status":"ok"}` when the build loaded; it does not test Shopify.

**Where the rest is.** The by-hand deploy, release folders and symlink rollback, systemd, nginx, TLS, rate limits, smoke test and the list of what is not verified are in [VPS_RUNBOOK](VPS_RUNBOOK.md) (maintained by devops; this document does not repeat them). Verified so far: 42 adapter tests and a run of the built storefront on a Windows developer machine against `bedding.mock.shop` (ADR-0011, "Verification"). **Not run on Linux, systemd or nginx.**

## Pipeline

Built: `.github/workflows/ci.yml` runs on every pull request and on pushes to `main`. It uses no secrets and no third-party action beyond the three GitHub-owned ones (`actions/checkout@v4.2.2`, `actions/setup-node@v4.4.0`, `actions/upload-artifact@v4.6.2`, each pinned to an exact version; commit SHAs when the repository moves to the client's organisation, T-12). It has **not run on a remote** yet (no remote repository, P1-06), so everything below was only rehearsed locally (see "What was verified" at the end of this section). The workflow has four jobs. The `concurrency` group is `ci-<ref>`; a newer push cancels an older run only for pull requests, so a push to `main` always finishes.

- Job `framework` (display name "Framework and docs", timeout 30 minutes, full clone): `node scripts/validate-framework.mjs`; a secret scan of the **whole git history** with plain `git grep` over every commit (same five token shapes as the validator, which scans only the current tree; prints paths, never the matched text; a `git grep` error fails the step instead of passing it); `node --test "scripts/**/*.test.mjs"`.
- Job `storefront` (display name "Storefront (format, lint, types, unit, build)", timeout 30 minutes, in `storefront/`): `npm ci`, `npm run format:check`, `lint`, `typecheck`, `test`, `build`, and a report-only `npm audit --omit=dev --audit-level=high` (`continue-on-error`, ADR-0008). No browser tests run here.
- Job `e2e-chromium` (display name "E2E (Chromium desktop and mobile)", timeout 75 minutes, **intended as a required check**): `npm ci`, `npx playwright install --with-deps chromium`, a step that writes three git-ignored placeholder env files on the runner (`.env.ci`, `.env.ci-delivery`, `.env.ci-protection`; names and meaning in [DEV_DATA](../../storefront/DEV_DATA.md#ci-github-actions)), a build step (`npm run build`, for run 4), then four Playwright invocations, each with its own `E2E_RUN_NAME` and a condition of `!cancelled()` plus the setup it needs, so one red run does not skip the others. Runs 1 to 3 need only the env-file step to have succeeded; run 4 also needs the build to have succeeded. The server each run starts reads its env file through `E2E_ENV_FILE` (`storefront/playwright.config.ts` adds `--env-file`; the value may hold only letters, digits, `_ . / -`, may not start with `-` and may not contain a `..` segment, or the config throws). A failing run fails the job. Its report is uploaded on failure as the artefact `playwright-report-chromium` (folders `storefront/playwright-report` and `storefront/test-results`, kept 7 days).
- Job `e2e-crossbrowser` (display name "E2E (WebKit and Firefox, not required)", timeout 120 minutes, `continue-on-error`): `npm ci`, `npx playwright install --with-deps webkit firefox`, its own `.env.ci`, and only run 1 below with `--project=desktop-webkit --project=mobile-webkit --project=desktop-firefox`, `E2E_ALL_BROWSERS=1` and `E2E_RUN_NAME=crossbrowser`. It is informational: WebKit and Firefox have never run against this suite, so there is no baseline. Promote it (remove `continue-on-error`, add it to the required checks) only after a few consecutive green runs. It uses the dev server like the Chromium job, on purpose, so a difference between the two jobs is the browser and nothing else. Report on failure: artefact `playwright-report-crossbrowser`.

Branch protection should require "Framework and docs", "Storefront (format, lint, types, unit, build)" and "E2E (Chromium desktop and mobile)", not the cross-browser job. **Branch protection is not configured** (there is no remote).

| Run | `E2E_RUN_NAME`            | Env file, port                                                                                           | Specs                                                   | Projects                                             |
| --- | ------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- | ---------------------------------------------------- |
| 1   | `run1-mock-store`         | `.env.ci`, 3100 (the default port)                                                                       | the whole suite (`npm run e2e`)                         | `desktop-chromium`, `mobile-chromium`                |
| 2   | `run2-delivery`           | `.env.ci-delivery`, 3700                                                                                 | `delivery`, `shell` (the zone tests that skip in run 1) | `desktop-chromium`, `mobile-chromium`                |
| 3   | `run3-protection`         | `.env.ci-protection`, 3900, `E2E_PROTECTION_FLAG=on`, the local Extend mock on 4010                      | `protection`, `resilience`                              | `desktop-chromium`, `mobile-chromium`                |
| 4   | `run4-production-preview` | `.env.ci`, 4400, `E2E_PROD_PREVIEW=1`, `vite preview` on the bundle built earlier in the job | `b20-production`                                        | `desktop-chromium`, `mobile-chromium`                |
| X   | `crossbrowser`            | `.env.ci` (in the other job), 3100                                                                       | the whole suite                                         | `desktop-webkit`, `mobile-webkit`, `desktop-firefox` |

`E2E_RUN_NAME` (letters, digits, `_ -`; the config throws otherwise) gives one invocation its own report folder `playwright-report/<name>` and results folder `test-results/<name>`. Playwright empties its output folders at the start of every run, so without a name a later run would erase the report and traces of an earlier failed one. Unset, the plain default folders are used.

All values in the env files are public placeholders (the dummy 32-character token bedding.mock.shop ignores, throwaway cookie secrets of 32 or more characters, the Extend mock's values); `PUBLIC_SITE_URL` is deliberately unset. Specs that need something a run does not supply skip themselves with a stated reason (for example `delivery` and the zone tests of `shell` in run 1, `protection` and `resilience` in run 1 without the flag), so run 1 reports them as skipped, not passed. **Skipped in CI by design:** `pickers.spec` success paths (a gift, add-on or bundle needs real offer data and variants, V-06, V-17), the haul-away and delivery-choice steps (`nodes(ids)` lookups the mock stores do not answer; unit-tested), and everything that needs the development store or the Extend demo host (V-02, V-16). The job timeouts (30, 30, 75 and 120 minutes) are ceilings, not measurements: only a three-spec subset was timed locally, so lower them after the first real run reports durations.

**Recommendations, not built (no new dependency without an owner decision, T-12):** a dedicated scanner such as gitleaks or trufflehog run once over the history before the repository transfer (it also finds entropy-based keys and non-listed formats that the five patterns miss), and pinning the three actions to commit SHAs.

**What was verified (2026-10-15, local, Node 22, no GitHub; before the split into four jobs):** the env-file step's script text was extracted from the workflow and run as written, then the Playwright commands of the runs were executed with `E2E_ENV_FILE`, `CI=true` (one retry) and the run's own port. The runs were not repeated with `E2E_RUN_NAME` and the job split is not rehearsed. Run 1 was `shell`, `catalog` and `cart` only, two Chromium projects, port 4950: 128 passed, 33 skipped, 1 flaky (passed on retry). Run 2: 92 passed, 31 skipped, 3 flaky delivery tests (passed on retry; the delivery ZIP specs are timing-sensitive on a cold dev server). Run 3 (mock started and stopped by the step's own script): 40 passed, 2 skipped. Run 4 (after `npm run build`): 8 passed. The history scan was run on every commit of this repository at the time (clean) and on a throwaway repository holding a deleted fake key, token and private key (caught). **Not verified until the first run on GitHub:** the workflow itself (YAML as GitHub parses it, `ubuntu-latest`, `--with-deps` installs, caching, artefact upload and the two artefact names); how the `!cancelled()` conditions and the `continue-on-error` job behave in practice (skips, overall workflow result); the `concurrency` rule that cancels only pull request runs; WebKit and Firefox, which have never run (no spec is tagged Chromium-only, so a failure there is possible on the first run); the full suite in run 1; the job durations; and that a failing check blocks merge (branch protection is not configured and needs a remote).

## Release and rollback

1. Tag a release candidate; run [deployment-readiness](../../.claude/skills/deployment-readiness/SKILL.md).
2. Record approval (who, when, which commit) in [DECISIONS](../../progress/DECISIONS.md).
3. Deploy; run read-only smoke checks; one authorised, refunded live test order for the first launch.
4. Rollback triggers (written in the Phase 9 runbook): checkout hand-off failing, sync failing beyond a set time, error rate spike, security issue. **Rollback:** Option A redeploys the previous Oxygen deployment; Option B points the process manager at the previous release directory and reloads Nginx (on the VPS plan: move the `current` symlink and restart the service, [VPS_RUNBOOK](VPS_RUNBOOK.md) section 11; not rehearsed). Config-only rollbacks: set `PUBLIC_EXTEND_ENABLED=false`, set `OFFERS_ENABLED=false` (only on purpose: it removes all offers), clear `PUBLIC_GIFT_PICKER_ENABLED`, or deactivate a discount in Shopify admin. Environment changes need a restart or redeploy as the host requires (unverified).
5. Rehearse rollback on staging before the first production release (none rehearsed yet).

## Backups and recovery

The storefront has no database (NFR-006); the repository and Shopify hold the state. Option B: document server rebuild from the repository plus secrets inventory; take configuration backups; the client or a maintenance agreement owns OS patching and backups (SOW §3).

## Monitoring

Built: structured, redacted logging with a closed event vocabulary (NFR-010); the alert table is in RUNBOOKS section 11 and has not been wired to any tool. Planned: a failed-sync alert, a reconciliation report schedule, and, for Option B, uptime monitoring for the site and the sync.
