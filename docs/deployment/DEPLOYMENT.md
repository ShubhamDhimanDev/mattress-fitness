# Deployment, environments and rollback

Status: strategy, 2026-10-11. Details are filled in during Phase 1 (staging) and Phase 9 (production). **Nothing is deployed or published automatically; every production deployment needs recorded human approval.** Hosting choice is open (Q-003): both options below stay viable until it is answered (ADR-0004).

## Environments

| Environment | Where | Data | Purpose | Deploys |
|---|---|---|---|---|
| Local | developer machine, Node 22 LTS | development store (or `mock.shop` early) | build and test | manual |
| Staging | our staging server during development (SOW §3) | development store, later a copy of the client's configuration | client review, daily link and change note, weekly demo | automatic from `main` after CI passes (staging only) |
| Preview (Option A) | Oxygen preview deployments per branch or change | development store | review of a single change | automatic per pull request once on Oxygen |
| Production | Oxygen (A) or the client's server (B) | client's Shopify store | live site | **manual, approved** |

## Environment variables

Names only; values stay in the hosting platform's secret store and in ignored local files. Exact names come from the scaffold (P1-03) and are reconciled with [.env.example](../../.env.example). `PUBLIC_` prefixed variables are exposed to browsers by Hydrogen's convention; everything else is server-only.

| Variable | Exposure | Origin |
|---|---|---|
| `SESSION_SECRET` | server | generated by us, one per environment; at least 32 characters in production. A missing or shorter value makes production refuse every request (HTTP 500) and logs the variable name once per isolate |
| `DELIVERY_COOKIE_SECRET` | server | generated by us, one per environment, different from `SESSION_SECRET`, at least 32 characters; signs the delivery ZIP cookie (without it the ZIP is not saved, the header shows no ZIP entry in production, and the variable name is logged once per isolate) |
| `PUBLIC_SITE_URL` | public | the storefront's own origin (`https://www.example.com`); canonical links, structured data and the sitemap use it, never the request Host. Without it they are omitted outside development |
| `PUBLIC_SUPPORT_PHONE` | public | the client's support phone (US number); no phone link is rendered until it is set (REQ-CNT-001) |
| `OFFER_CONFIG_JSON` | server | non-secret JSON with the offer rules and the delivery zone; a temporary seam until the metaobject-backed rules exist (P4-12). In production a missing or invalid value pauses checkout with an explanation |
| `OFFERS_ENABLED` | server | set to `false` only to run without offers on purpose; any other value, or none, leaves the offer gate on |
| `PUBLIC_STORE_DOMAIN` | public | client's Shopify store (myshopify domain) |
| `PUBLIC_STOREFRONT_ID` | public | Hydrogen or Headless channel |
| `PUBLIC_STOREFRONT_API_TOKEN` | public | channel's public Storefront API token |
| `PRIVATE_STOREFRONT_API_TOKEN` | server | channel's private token |
| `PUBLIC_CHECKOUT_DOMAIN` | public | store's checkout domain |
| `PUBLIC_CUSTOMER_ACCOUNT_API_CLIENT_ID`, `PUBLIC_CUSTOMER_ACCOUNT_API_URL` | public | Customer Account API settings in the channel |
| `SHOP_ID` | server in the scaffold (Customer Account API); do not expose to the browser unless Hydrogen's analytics requires it | Shopify store ID |
| `SHOPIFY_APP_CLIENT_ID`, `SHOPIFY_APP_CLIENT_SECRET` | server | Dev Dashboard app with custom distribution on the client's store (legacy custom apps cannot be created, V-20); least-privilege scopes. **The client secret also verifies webhook signatures** (ADR-0009 addendum); there is no separate webhook secret. The access token is obtained at runtime or stored in the platform secret store, never in the repo |
| `SHOPIFY_ADMIN_API_ACCESS_TOKEN` | server | offline token from the authorization-code grant; a SEPARATE token with the `read_orders` scope only, used by the webhook route to read one order. Never the catalog import token, which can write |
| `EXTEND_API_HOST`, `EXTEND_STORE_ID`, `EXTEND_ACCESS_TOKEN` | server | Extend: `EXTEND_API_HOST` is the local mock, `https://api-demo.helloextend.com` or `https://api.helloextend.com`; token from a Merchant Portal API Integration (F-27) |
| `SHOPIFY_STORE_DOMAIN`, `SHOPIFY_ALLOWED_STORES`, `SHOPIFY_ADMIN_API_VERSION` | **scripts only** | Used by `scripts/catalog` and `scripts/shopify`. Live runs refuse any store not in `SHOPIFY_ALLOWED_STORES`. Never set in a storefront deployment |
| `JUDGEME_PRIVATE_API_TOKEN` | server | Judge.me private key if Judge.me is chosen (Q-011); never a `PUBLIC_` variable |
| `PUBLIC_EXTEND_ENABLED` | public | our feature switch (non-secret); `false` hides every Extend surface |
| `EXTEND_ORDER_SYNC` | server | `self` (default), `extend-app` or `off`; guards against double reporting (ADR-0009) |
| `PUBLIC_GA4_MEASUREMENT_ID`, `PUBLIC_META_PIXEL_ID`, `PUBLIC_KLAVIYO_COMPANY_ID` | public | client accounts (CLR-004) |
| `PUBLIC_AFFIRM_PUBLIC_KEY` | public | Affirm (Q-016) |
| `PUBLIC_MAPS_API_KEY` | public (restricted by referrer) | maps provider if any (Q-010) |

### Production readiness: settings that fail silently or closed

Check these on every environment before go-live (also IR-27 in [READINESS_CHECKLIST](../integrations/READINESS_CHECKLIST.md)). A mistake here does not show as a build error.

- `SESSION_SECRET` and `DELIVERY_COOKIE_SECRET`: each at least 32 random characters and different from each other. Production logs the variable name once per isolate when one is wrong; look for `[config]` lines after the first deploy.
- `PUBLIC_SITE_URL`: set to the live origin, or canonical links and structured data are missing.
- `OFFER_CONFIG_JSON` (and `OFFERS_ENABLED` only if offers are deliberately off): valid, or checkout is paused.
- `SHOPIFY_APP_CLIENT_SECRET`: set, or webhook signatures cannot be verified and the Extend sync rejects every event.
- `SHOPIFY_ADMIN_API_ACCESS_TOKEN`: the `read_orders`-only token, and `PUBLIC_STORE_DOMAIN` must be the `<shop>.myshopify.com` domain for that read.
- `EXTEND_ORDER_SYNC` and `PUBLIC_EXTEND_ENABLED`: the intended values, so Extend orders are reported once and the Extend surfaces show only when ready.
- `PUBLIC_SUPPORT_PHONE`: the client's number, or no phone link appears.

## Pipeline (to be implemented)

CI on every pull request: install from lockfile, format, lint, type check, unit, build, e2e, dependency audit, secret scan, `node scripts/validate-framework.mjs`. Staging deploys from `main` after CI. Production deploy is a separate, manually approved job tied to a tagged release; it uses the same artefact that passed CI.

## Release and rollback

1. Tag a release candidate; run [deployment-readiness](../../.claude/skills/deployment-readiness/SKILL.md).
2. Record approval (who, when, which commit) in [DECISIONS](../../progress/DECISIONS.md).
3. Deploy; run read-only smoke checks; one authorised, refunded live test order for the first launch.
4. Rollback triggers (written in the Phase 9 runbook): checkout hand-off failing, sync failing beyond a set time, error rate spike, security issue. **Rollback:** Option A redeploys the previous Oxygen deployment; Option B points the process manager at the previous release directory and reloads Nginx. Config-only rollbacks: toggle `PUBLIC_EXTEND_ENABLED` or deactivate an offer or discount in Shopify admin.
5. Rehearse rollback on staging before the first production release.

## Backups and recovery

The storefront has no database (NFR-006); the repository and Shopify hold the state. Option B: document server rebuild from the repository plus secrets inventory; take configuration backups; the client or a maintenance agreement owns OS patching and backups (SOW §3).

## Monitoring

Option B: uptime monitoring and alerting for the site and the sync service. Both options: structured error logging with redaction (NFR-010), a failed-sync alert, and a reconciliation report schedule.
