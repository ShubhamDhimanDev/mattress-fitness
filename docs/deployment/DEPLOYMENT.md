# Deployment, environments and rollback

Status: strategy dated 2026-10-11; environment variables, pipeline and host-dependent items reconciled with the code on 2026-10-15 (branch `feat/p6-account-p7-seo-perf`, main at `81a29a9`). **Nothing is deployed or published automatically; every production deployment needs recorded human approval.** Hosting choice is open (Q-003): both options below stay viable until it is answered (ADR-0004). No staging server exists yet (P1-07 is blocked) and no deployment command has been run; everything about Oxygen or an own server below is a plan, not an experience. What this document does not cover: DNS and cutover (P9-03, P9-04), server hardening for Option B, analytics and reviews providers.

## Environment variables

Names only; values stay in the hosting platform's secret store and in git-ignored local files (`.env`, `.env.*`; only `.env.example` is tracked). The list below was cross-checked on 2026-10-15 against [.env.example](../../.env.example) and a search of `storefront/app/`, `storefront/server.ts` and `scripts/` for each name. `PUBLIC_` prefixed variables are exposed to browsers by Hydrogen's convention; everything else is server-only. Code reads variables from the request-context `env` only (ADR-0004).

"Fails" says what happens in a **production build** when the variable is missing or wrong. Dev servers are more lenient where stated.

Under 32 characters in production: same, and `config.secret_unusable` names the variable once per isolate. Development accepts a short value but still needs one |

### Reserved: listed in `.env.example`, read by no code today

`SHOPIFY_APP_CLIENT_ID`, `JUDGEME_PRIVATE_API_TOKEN` (never `PUBLIC_`), `PUBLIC_GA4_MEASUREMENT_ID`, `PUBLIC_META_PIXEL_ID`, `PUBLIC_KLAVIYO_COMPANY_ID`, `PUBLIC_AFFIRM_PUBLIC_KEY`, `PUBLIC_MAPS_API_KEY` (restricted by referrer). ### Scripts only (`scripts/catalog`, `scripts/shopify`, `scripts/extend`, `scripts/detective`)

`SHOPIFY_STORE_DOMAIN`, `SHOPIFY_ALLOWED_STORES`, `SHOPIFY_ADMIN_API_ACCESS_TOKEN`, `SHOPIFY_ADMIN_API_VERSION`; the Extend scripts also read `EXTEND_API_HOST`, `EXTEND_STORE_ID`, `EXTEND_ACCESS_TOKEN`; the detective report reads `OFFER_CONFIG_JSON`; the local Extend mock reads `EXTEND_MOCK_ACCESS_TOKEN` and `EXTEND_MOCK_STORE_ID`. Any contact with a store needs the domain in `SHOPIFY_ALLOWED_STORES`; writes also need `--live`. **Never set `SHOPIFY_STORE_DOMAIN`, `SHOPIFY_ALLOWED_STORES` or a write-capable token in a storefront deployment.** The same variable name `SHOPIFY_ADMIN_API_ACCESS_TOKEN` holds a different token in each place: `read_orders` only on the server; a product-write token only in a developer's shell for the importer.

### Production readiness: settings that fail silently or closed

Check these on every environment before go-live (also IR-27 in [READINESS_CHECKLIST](../integrations/READINESS_CHECKLIST.md)). A mistake here does not show as a build error.

- `SESSION_SECRET` and `DELIVERY_COOKIE_SECRET`: each at least 32 random characters and different from each other. Look for `config.secret_unusable` lines after the first deploy.
- `PUBLIC_SITE_URL`: the live origin, or canonical links and structured data are missing.
- `OFFER_CONFIG_JSON` (and `OFFERS_ENABLED` only if offers are deliberately off): valid, or checkout is paused.
- `SHOPIFY_APP_CLIENT_SECRET`: set, or the webhook answers 503.
- `SHOPIFY_ADMIN_API_ACCESS_TOKEN`: the `read_orders`-only token, with `PUBLIC_STORE_DOMAIN` set to the `<shop>.myshopify.com` domain.
- `EXTEND_API_HOST` not the mock; `EXTEND_ORDER_SYNC` and `PUBLIC_EXTEND_ENABLED` at the intended values.
- `PUBLIC_GIFT_PICKER_ENABLED` unset until V-03 passes.
- `PUBLIC_SUPPORT_PHONE`: the client's number, or no phone link appears.
- The `/webhooks/shopify` subscription exists on the app for `orders/paid`, `orders/updated`, `orders/cancelled`, `refunds/create`, `fulfillments/create` (V-20; not yet created anywhere).

## Pipeline

Built: `.github/workflows/ci.yml` runs on every pull request and on pushes to `main`. Job `framework`: `node scripts/validate-framework.mjs` and `node --test "scripts/**/*.test.mjs"`. Job `storefront` (in `storefront/`): `npm ci`, `npm run format:check`, `lint`, `typecheck`, `test`, `build`, a non-blocking `npm audit --omit=dev --audit-level=high` (ADR-0008), `npx playwright install --with-deps chromium webkit firefox` and `npm run e2e` with `E2E_ALL_BROWSERS=1`. It uses no secrets. It has **not run on a remote** yet (no remote repository, P1-06). Two things to check on its first run: the e2e job starts `npm run dev` with no env file, but the app needs `SESSION_SECRET` even in development, so the job likely needs an env step (not verified); and the workflow has no dedicated secret-scan step: only the framework job's `validate-framework.mjs` scans the tree for token-shaped strings, and P1-06 and REQ-HAND-001 also expect a history scan before transfer.

Planned, not built: staging deploy from `main` after CI; a production deploy as a separate, manually approved job tied to a tagged release, using the same artefact that passed CI; a history scan and a dedicated secret scanner.

## Release and rollback

1. Tag a release candidate; run [deployment-readiness](../../.claude/skills/deployment-readiness/SKILL.md).
2. Record approval (who, when, which commit) in [DECISIONS](../../progress/DECISIONS.md).
3. Deploy; run read-only smoke checks; one authorised, refunded live test order for the first launch.
4. Rollback triggers (written in the Phase 9 runbook): checkout hand-off failing, sync failing beyond a set time, error rate spike, security issue. **Rollback:** Option A redeploys the previous Oxygen deployment; Option B points the process manager at the previous release directory and reloads Nginx. Config-only rollbacks: set `PUBLIC_EXTEND_ENABLED=false`, set `OFFERS_ENABLED=false` (only on purpose: it removes all offers), clear `PUBLIC_GIFT_PICKER_ENABLED`, or deactivate a discount in Shopify admin. Environment changes need a restart or redeploy as the host requires (unverified).
5. Rehearse rollback on staging before the first production release (none rehearsed yet).

## Backups and recovery

The storefront has no database (NFR-006); the repository and Shopify hold the state. Option B: document server rebuild from the repository plus secrets inventory; take configuration backups; the client or a maintenance agreement owns OS patching and backups (SOW §3).

## Monitoring

Built: structured, redacted logging with a closed event vocabulary (NFR-010); the alert table is in RUNBOOKS section 11 and has not been wired to any tool. Planned: a failed-sync alert, a reconciliation report schedule, and, for Option B, uptime monitoring for the site and the sync.
