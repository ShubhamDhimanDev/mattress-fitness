## Configuration

| Variable                    | Effect                                                                                                                                                                     |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PUBLIC_GA4_MEASUREMENT_ID` | `G-` plus 4 to 16 letters or digits. Unset or malformed: GA4 is off, no script, no CSP host, no analytics checkbox                                                         |
| `PUBLIC_META_PIXEL_ID`      | digits only (6 to 20). Unset or malformed: Meta is off, same                                                                                                               |
| `PUBLIC_CONSENT_MODE`       | `opt-in` (default) or `opt-out`. **Only the exact text `opt-out` loosens it.** Any other value (`OPT-OUT`, `opt-out`, a typo) means `opt-in`: no trimming, no case folding |

Both ids unset: no consent state, no runtime, no banner, no script, no CSP change, and `<Analytics.Provider>` is called exactly as before (no `canTrack`). Names only are in the root `.env.example`.

**The legal choice is not made here.** `opt-in` is the stricter default. Whether the client may use `opt-out` for US visitors (and whether Global Privacy Control must be honoured) is a legal decision for the client (Q-012, T-16); changing it is one environment variable.

## Consent mechanics

- The banner is fixed to the bottom edge, renders only after hydration (server and first client render agree: "decided"), so it adds no layout shift. It is a labelled region, not a modal: focus is not taken, the page stays usable, and it comes before the header in the DOM so keyboard users meet it early. Accept all and Reject all are the same size and one press each; "Choose" opens a dialog (existing `Dialog`, focus return and Escape included) with one checkbox per configured category.
- **Withdrawal:** `PrivacyChoicesButton` reopens the preferences. It sits in the footer's bottom row with the legal links (`SiteFooter.tsx`), rendered only in the browser after hydration (the consent store does not exist on the server) and only when a provider id is set; otherwise its list item is empty and hidden. Unit-tested (`tests/unit/ui/footerPrivacyChoices.test.tsx`); not yet seen in a browser.
- **What the banner claims (review L-3).** It says the Google and Meta tools wait for the shopper's agreement, which is true. It does **not** say nothing at all is sent: Shopify's own sales-channel analytics (Hydrogen's `ShopifyAnalytics`, Shopify's consent script from `cdn.shopify.com`, `monorail-edge.shopifysvc.com`) follows Shopify's customer-privacy settings for the store, not this banner, and in the US default it can run before and after "Reject all". `withPrivacyBanner: false` (pre-existing) hides Shopify's own banner. Whether Shopify's analytics should also wait is a decision for the client with counsel (it would be a change to `canTrack`), and the privacy policy must describe it.
- On withdrawal the runtime asks the adapter to stop (GA4's `ga-disable-<id>` flag, Meta's `consent revoke`), drops queued events and expires `_ga`, `_ga_<id>`, `_fbp` and `_fbc` on the host **and on every parent suffix of two labels or more** (`www.shop.example.com` gives `www.shop.example.com`, `shop.example.com`, `example.com`, each with and without a leading dot), because GA4 and the pixel set them on the registrable domain (review L-2). No public-suffix list is used: a suffix such as `co.uk` is refused by the browser and harmless. A cookie with another path than `/` could survive; unverified in a browser.
- Cross-tab (review L-6): a `storage` event re-reads the decision, and so does every `focus` and every `visibilitychange` to visible, because the cookie, the primary store, emits no event; a withdrawal in another tab therefore stops sending here the next time the shopper looks at this tab (`attachConsentRefresh`). Cookies and storage can be blocked: the choice then holds for the visit and the shopper is asked again next time.

## Bundle budget and the lazy consent chunk (scripts/perf, NFR-002)

The consent layer first shipped in the initial JavaScript of every route and pushed `npm run perf:bundle` over its budgets (about +14 kB gzip). It is now split:

- **In the initial JavaScript (every route):** `AnalyticsGate` (Hydrogen's provider plus a request for the lazy chunk), `app/lib/analytics/gate.ts` (the published-store handle, `canTrack`, idle scheduling), the footer's `PrivacyChoicesButton`, `app/lib/analytics.ts` (`track`, which holds up to 25 early events), and, for product cards, `app/lib/listing-analytics.ts` (the one `data-si` attribute; it imports only `~/lib/format`). `item-basics.ts` (item builders, `selectItemValue`) and `listing-events.ts` are in the lazy part.
- **Lazy chunk `ConsentRuntime` (about 26 kB raw, loaded only when a provider id is set, after hydration and when the browser is idle, `requestIdleCallback` with a 3 s limit; a 1.5 s timer in Safari):** the consent store, the runtime, GA4 and Meta adapters, the script loader, the event mappers (`hydrogen-events.ts`), the privacy filters, the safe-page guard, the banner and the preferences dialog.
- With **neither id set (the default) the chunk is never requested**: no consent or provider code runs, and `<Analytics.Provider>` is rendered as before (no `canTrack`). Unit-tested (`tests/unit/analytics/gate-lazy.test.tsx`).
- A chunk that fails to download (offline, a deploy replaced the file, an ad blocker) hides the consent layer and nothing else (`gate-lazy-failure.test.tsx`).
- Consequences to know: the banner appears after the chunk has loaded, so up to about 3 s after the page is usable, rather than at hydration (it is fixed to the viewport, so nothing shifts). The page's first events (the page view, the listing, a Hydrogen view) happen before the chunk registers its sink, so `track()` holds them and replays them in order on registration; the runtime still drops what consent does not allow. Hydrogen's `canTrack` is Shopify's own answer until the chunk has published its store; the provider re-renders when it does, and Hydrogen publishes the current page again, so a returning shopper who already agreed is counted once.
- Rules that keep it small, found by measuring: a module imported by both an initial route chunk and the lazy chunk can become a separate chunk that every route downloads (`when-idle`, `Field`, `consent-context` and `gate` each did, 0.15 to 0.4 kB gzip each), so the shell passes its helpers to the chunk as props and the preferences dialog does not import `ui/Checkbox`. Vite's preload map for the lazy import (17 file names) adds about 0.3 kB gzip to the root chunk; avoiding it would need `build.modulePreload.resolveDependencies` in `vite.config.ts`, which is outside this task.

## Loading rules (NFR-011, NFR-013)

1. No script is requested for a category that is not allowed. Verified by unit test (`runtime.test.ts`); **not yet by a browser** (the e2e spec asserts zero provider requests before a decision).
2. After consent the load is scheduled with `whenIdle` (`requestIdleCallback`, Safari fallback timer), `async`, never blocking render. A script is added only from `https://www.googletagmanager.com` or `https://connect.facebook.net`; any other origin is refused before a script element exists.
3. The page the shopper is on is held in memory (only the latest `page_view`, never sent) and reported once they agree. Events that arrive while a consented script loads are queued (25 at most) and replayed in order.
4. Load failure (ad blocker, CSP refusal, outage, 10 s timeout) marks the provider failed for the visit, logs one `analytics.provider_failed` line with provider and reason only, and carries on. No retry loop. A thrown error in an adapter, in `send` or in the failure callback is swallowed.
5. No Subresource Integrity: both vendors serve these files at fixed, unversioned URLs that change without notice, so a pinned hash would break the integration. Mitigation: the origin allow-list, the nonce and the report-only policy.
6. **No load and no event on a page that fails the safe-page check** (review L-4, M-1): consent given on `/account/*`, `/track-order`, `/delivery` or `/checkout-steps` does not start a script; the first safe page after it does. A script already resident (single-page navigation cannot unload it) is paused on such a page (GA4's disable flag), so its automatic hits stop too, and resumed on the next safe page. Details below.

## Event mapping

Hydrogen publishes `product_viewed`, `search_viewed`, `cart_viewed`, `product_added_to_cart` and `product_removed_from_cart`; `AnalyticsBridge` subscribes and maps them. It does **not** subscribe to `collection_viewed` (and `mapCollectionViewed` answers null): `view_item_list` for every listing, collection pages included, comes from the listing code with the products, so the list is counted once. `page_view` and `begin_checkout` are sent by the bridge itself. Hydrogen publishes only while `canTrack` allows it; with a provider configured `canTrack` is "any category allowed, or Shopify's own consent answer", and Hydrogen republishes the current page when that changes, so a shopper who agrees later is counted once.

### Privacy (T-05, REQ-ANL-002)

- Cart payloads from Hydrogen also hold the buyer's email, name and phone; the mapper reads named fields only and never spreads, and a test asserts none of them reach the output.
- Parameter names are an allow-pattern; names suggesting personal data (email, phone, zip, address, name, customer, order id or number, card, token, secret) and values that look like an email or hold seven or more digits are dropped; strings are cut at 100 characters; at most 25 parameters.
- The page address WE report (the `page_location` parameter and the GA4 `set`) keeps origin, path and only `utm_*`, `gclid`, `fbclid`. Search words, filters, ZIP and other query strings stay out; the private paths are cut to their section. **This is not what the providers' own scripts read**: see the next section, which is the control for that.
- Search terms are sent (REQ-ANL-001 lists the `search` event) after the same email and digit check. A shopper can still type something personal that does not look like an email or a long number; this is a residual risk.
- Meta: `autoConfig` is turned off so the pixel does not scrape form fields or buttons; **hashed advanced matching is not implemented**; no email, phone, ZIP, name or order number is passed. Google signals and ad personalisation are off for GA4; GA4 sends no automatic page view.

## Safe pages and what the providers see (review M-1, L-4; T-05, T-10)

Google's and Meta's scripts read the page address, the title and the referrer themselves and attach them to every hit; only the one `page_view` we send carried our reduced address, so an earlier version of this document overstated what was enforced. Two controls now exist, both in `app/lib/analytics/page-context.ts` and applied by the runtime on every event:

1. **A page that fails the check sends nothing.** No event (Meta `PageView` included), no script load, and a loaded Google tag is paused there (so its automatic events, such as engagement and scroll, stop too). A page fails when:
   - it is in the private area: `/account` and everything under it (order pages included), `/track-order`, `/delivery`, `/checkout-steps`, `/discount` (matched after decoding, lower-casing and collapsing slashes, so `/ACCOUNT`, `//account` and `/%61ccount` fail too; `/accounting` and `/pages/delivery` do not). `/cart` is allowed;
   - any query value (except opaque click ids such as `gclid`, `fbclid`, `_kx`) looks personal (an email, or seven or more digits), or the path holds an email;
   - it is a search page whose `q` looks personal.
2. **On a page that passes, Google is told the reduced values** with `gtag('set', {page_location, page_referrer, page_title})` before `config` and again on every navigation, so later events (in the hope of the automatic ones too) inherit them: address with campaign tags only (no `q`, no filters); title is the fixed word **`Search`** on search pages (the real title is `Search: <term>`) and otherwise the page title unless it looks personal (then `Page`); referrer is the origin only for another site, and for an own page the reduced address (no search words, private pages cut to the section such as `/account`). Order pages never reach this point: neither their path nor their title is reported, because they send nothing.

What remains, honestly:

- **Meta cannot be overridden.** On a search page whose term passes the check, the pixel still reads the real address including `?q=<term>`, and probably the referrer. The same term is also sent as `search_string`, so no new data leaves, but a free-text term that is personal and does not look like an email or a long number (`123 Main St`) goes to both. Residual risk, to be covered in the privacy policy (review I-4). Meta's own use of the page address is not documented (UNVERIFIED).
- **Whether `gtag('set', ...)` reaches GA4's automatic events is UNVERIFIED** (DebugView). If it does not, the pause on private pages and the check above are still what protects them; on a safe page the automatic events (such as `scroll`) carry the real address, which by the check holds nothing personal except that a search page's `q` may appear (and is then also sent as the search term).
- A resident script stays in the document after the shopper reaches a private page by in-app navigation; it is paused, not removed. Reloading the private page starts clean.

## GA4 administration checklist (for the client, before go live; review M-1)

Done in the GA4 property by someone with Editor access; none of it can be done or checked from this code.

1. **Admin, Data streams, the web stream, Enhanced measurement**: turn off **Site search** (it reads `q`, `s`, `search`, `query`, `keyword` from the address), **Form interactions** and **Outbound clicks** (or accept them knowingly and record that). Review Page changes (history events) and Scroll tracking: on, they are acceptable, but they must not be doubled by our own `page_view` (we send it manually, and `send_page_view` is off).
2. **Admin, Data collection and modification, Data redaction**: turn on **Email address redaction** and add **query parameter keys** to redact: `q`, `login_hint`, `_kx` and any other key the client's email or marketing tool adds to links.
3. **Admin, Data collection and modification, Data retention**: set **Event data retention** to the shortest value the client accepts (2 months or 14 months) and record the choice for the privacy policy.
4. **Google signals** stays off (the code sets `allow_google_signals: false`; the property setting should agree); **Ads personalization** stays off; do not link Google Ads without a new review (CSP and consent categories change).
5. **Data sharing settings**: turn off any sharing the client does not need (technical support, account specialists, benchmarking).
6. Verify in **DebugView** with the staging site: the `page_location`, `page_title` and `page_referrer` values on `page_view`, `view_item`, `add_to_cart` and on an automatic event such as `user_engagement`; a search page shows `Search` and no term in the address; an account or order page produces no event at all. Record the evidence in `progress/TEST_RESULTS.md`.

## Content Security Policy (T-10)

Added **only** when the matching id is set, to the report-only policy (`buildReportOnlyCsp`) and to Hydrogen's enforced policy (`enforcedCspExtras`, passed to `createContentSecurityPolicy`). Which of the two is enforced is unchanged: Hydrogen's stays enforced, the tightened one stays report-only.

| Provider | script-src                         | img-src                                                              | connect-src                                                                                                                                                      | Source                                                                                                                                                                                                                   |
| -------- | ---------------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| GA4      | `https://www.googletagmanager.com` | `https://www.googletagmanager.com`, `https://*.google-analytics.com` | `https://www.googletagmanager.com`, `https://*.google-analytics.com`, `https://www.google.com`, `https://analytics.google.com`, `https://*.analytics.google.com` | Google's CSP guide, "Analytics without Ads features", read 2026-10-23 (developers.google.com/tag-platform/security/guides/csp), **narrowed**: Google's `https://*.google.com` for `connect-src` is not used (review L-1) |
| Meta     | `https://connect.facebook.net`     | `https://www.facebook.com`                                           | `https://www.facebook.com`, `https://connect.facebook.net`                                                                                                       | **UNVERIFIED.** Meta's documentation says nothing about CSP (checked 2026-10-23); the hosts come from community and vendor guides. Review the console in report-only mode with a real pixel                              |

- Naming `script-src` or `img-src` in Hydrogen's policy replaces the `default-src` fallback (self, nonce, cdn.shopify.com, shopify.com), so those Shopify sources are repeated and only the provider hosts are added; the nonce is appended by Hydrogen. With no provider set, nothing is passed and the policy is byte-for-byte what it was (tested).
- **Exception to `docs/security/SECURITY_HEADERS.md` ("never a wildcard host"), needing the project owner's WRITTEN approval; not given.** Two wildcards are used, each limited to one Google-operated, analytics-only registrable domain, in `img-src` and `connect-src` only: `https://*.google-analytics.com` (regional collectors such as `region1.google-analytics.com`; an exact list would silently lose data, and an exact host would not stop exfiltration to an attacker's own GA property anyway) and `https://*.analytics.google.com`. The security review (L-1) recommends accepting `*.google-analytics.com` and narrowing `*.google.com` (done, above). A comment in `hosts.ts` and a test (`csp.test.ts`) say the same: the only wildcards that may appear are those two, and none in `script-src`.
- `https://*.google.com` is **not** allowed for connections. `google.com` serves user-controlled content (`script.google.com` web apps, `docs.google.com`, `sites.google.com`, forms), so it would be a ready-made data sink for any future script injection. Instead `connect-src` names `https://www.google.com`, `https://analytics.google.com` and `https://*.analytics.google.com`. **Which of these GA4 actually calls with Google signals and ad personalisation off is UNVERIFIED.** Run staging in report-only with a real measurement id, load every template with the console open, and **add only the hosts actually seen blocked**; remove any of the three that is never used.
- GTM server-side or first-party mode is not required (review L-1): it needs a hosted container and a custom domain and helps ad blockers rather than CSP risk. Revisit if Google Ads, Meta Conversions API or a larger tag estate arrives. If `script-src-elem` is ever added to the policy, the provider script hosts must be added there too (Google's guide names `script-src-elem`; today only `script-src` is set, which is equivalent).
- No `'unsafe-inline'`, no `'unsafe-eval'` for scripts. The scripts are added with the page nonce.
- `docs/security/SECURITY_HEADERS.md` ("Third-party allow-list policy") still says no third-party origin is allowed and should be updated by its owner with this table (not edited here).

### Review items recorded as accepted or open (security review 2026-10-24)

- **L-5, open (counsel):** Global Privacy Control is read only while undecided and only in opt-out mode, only for marketing; a stored choice always wins, including an acceptance given before the browser started sending the signal, and GPC does not reduce what "Accept all" turns on in opt-in mode. For California and several other states GPC is a binding opt-out of sale or sharing and the Meta pixel is a likely "sharing" case. Not changed here; recommendation for the client's counsel: honour GPC for `marketing` in both modes and over an older stored acceptance. Part of the legal review (Q-012).
- **L-7, accepted (revisit if the client runs untrusted subdomains):** `mf_consent` is unsigned and host-only (no `Domain`). A sibling subdomain able to set a parent-domain cookie of that name could forge "accepted" for that shopper's browser; the effect is limited to turning analytics on for that shopper.
- **I-2, accepted:** no Subresource Integrity (mutable vendor files); compensating controls are the origin allow-list in the loader, per-id CSP hosts, consent and idle gating, and the nonce. A compromise at Google or Meta would still run with page privileges (T-10).
- **I-4, open (privacy policy):** free text that passes the filter (`mattress 90210`, `123 Main St`) is sent as `search_term` and `search_string`; the privacy policy must say search words are shared.
- **I-5, open (client):** `utm_*`, `gclid`, `fbclid` are kept in the reported address; `fbclid` becomes `_fbc`. Retention is the GA4 property setting in the checklist above; record the chosen value in the privacy policy.
- **Privacy policy page:** `/policies/privacy-policy` (linked from the banner) must exist and match practice before any id is set (the review's list: who, what, why and how long, choices, the ZIP cookie that is not sent to analytics, Shopify's own analytics).
