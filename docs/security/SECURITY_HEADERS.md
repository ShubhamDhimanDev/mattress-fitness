### HSTS: not done, on purpose

`includeSubDomains` and `preload` are **not** sent. Both are effectively permanent and need (a) the final host and domain (Q-003) and (b) an inventory of every subdomain of the client's domain, because `includeSubDomains` forces https on all of them. Ramp: keep six months until launch plus a month of clean traffic, raise to one year, and only then consider `includeSubDomains` and the preload list, as a separate decision. Terminate TLS and redirect http to https at the host or edge; this header does not do that.

## The report-only policy and why it is tighter

Hydrogen's enforced policy is `default-src 'self' 'nonce-X' https://cdn.shopify.com https://shopify.com`, plus `style-src ... 'unsafe-inline'`, `connect-src` and `frame-ancestors 'none'`. Everything not listed falls back to `default-src`, which also allows Shopify's account host for scripts, plugins and form targets. The report-only variant:

| Directive                                | Sources                                                                           | Difference from the enforced policy                                               |
| ---------------------------------------- | --------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `default-src`                            | `'self'`                                                                          | no longer includes the nonce, the CDN or `shopify.com`                            |
| `script-src`                             | `'self'`, `'nonce-X'`, `https://cdn.shopify.com`                                  | `shopify.com` removed from scripts (Hydrogen's consent script loads from the CDN) |
| `script-src-attr`                        | `'none'`                                                                          | no inline event handlers                                                          |
| `style-src`                              | `'self'`, `https://cdn.shopify.com` (dev adds `'unsafe-inline'` for Vite)         | no inline `<style>` elements                                                      |
| `style-src-attr`                         | `'unsafe-inline'`                                                                 | React `style=""` attributes only                                                  |
| `img-src`                                | `'self'`, `data:`, `https://cdn.shopify.com`                                      | explicit, instead of the fallback                                                 |
| `font-src`, `media-src`                  | `'self'`, `https://cdn.shopify.com`                                               | explicit                                                                          |
| `connect-src`                            | `'self'`, CDN, `https://monorail-edge.shopifysvc.com`, checkout and store domains | same as Hydrogen's                                                                |
| `object-src`, `frame-src`                | `'none'`                                                                          | new                                                                               |
| `worker-src`, `manifest-src`, `base-uri` | `'self'`                                                                          | new or same                                                                       |
| `form-action`                            | `'self'`, `https://shopify.com`, checkout and store domains                       | new; the customer-account sign-in and sign-out leave through `shopify.com`        |

`frame-ancestors` is left out because browsers ignore it in a report-only policy; the enforced policy sends `'none'`. Shop domains come from `PUBLIC_STORE_DOMAIN` and `PUBLIC_CHECKOUT_DOMAIN` and are accepted only as plain DNS names, so an odd environment value cannot add a directive. A nonce that is not a plain token produces no header.

**Verification so far:** unit tests (`app/lib/security-headers.test.ts`, table-driven cases including injected domains and nonces); the dev server on 2026-10-15 sent every header on `/`, on `.data` requests and on `robots.txt` and `sitemap.xml`; the e2e spec `tests/e2e/seo-headers.spec.ts` loads the home page in desktop and mobile Chromium and sees **no** policy violation in the console. **Not done:** a production build served on a real host (production lists no `localhost` sources), a check of the customer-account sign-in flow under `form-action`, and the checkout hand-off.

## Reports

Violations show in the browser console only. There is no collector: adding `report-uri` or `report-to` means choosing a receiving endpoint (a third-party service is a T-10 decision, a self-hosted route is an abuse target, T-13) and depends on the host (Q-003). Until then review by loading each template (home, collection, product, cart, search, stores, quiz, compare, blog, account) in Chromium with the console open.

## Third-party policy: analytics and Meta (P7-01, T-10; added 2026-10-23)

**Default: no third-party origin.** With neither `PUBLIC_GA4_MEASUREMENT_ID` nor `PUBLIC_META_PIXEL_ID` set (or with a malformed value, which counts as unset), both policies contain only the site itself and Shopify (`cdn.shopify.com`, `shopify.com`, `monorail-edge.shopifysvc.com`, the store and checkout domains). A unit test (`app/lib/security-headers.test.ts`, "allows no third-party origin yet") fails if the report-only policy gains any other origin, and `tests/unit/analytics/csp.test.ts` asserts the policy is byte-for-byte unchanged with no id set.

**A provider's hosts are added only when its id is set** (`parseAnalyticsConfig` in `entry.server.tsx`; `analyticsCspHosts` in `app/lib/security-headers.ts`). The list lives in one file, `storefront/app/lib/analytics/hosts.ts`, which also holds the quoted source and the open questions:

| Provider (set by)                 | `script-src`                       | `img-src`                                                            | `connect-src`                                                                                                                                                    |
| --------------------------------- | ---------------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GA4 (`PUBLIC_GA4_MEASUREMENT_ID`) | `https://www.googletagmanager.com` | `https://www.googletagmanager.com`, `https://*.google-analytics.com` | `https://www.googletagmanager.com`, `https://*.google-analytics.com`, `https://www.google.com`, `https://analytics.google.com`, `https://*.analytics.google.com` |
| Meta (`PUBLIC_META_PIXEL_ID`)     | `https://connect.facebook.net`     | `https://www.facebook.com`                                           | `https://www.facebook.com`, `https://connect.facebook.net`                                                                                                       |

- **Sources.** Google's list is taken from Google's own guide, "Use Google tag with a Content Security Policy" (developers.google.com/tag-platform/security/guides/csp, "Analytics without Ads features", read 2026-10-23), **narrowed**: Google's `https://*.google.com` for `connect-src` is deliberately not used, because `google.com` serves user-controlled content and would be a ready-made data sink after any future script injection (security review L-1). Which of the three named connect hosts GA4 really calls is **unverified**: run staging in report-only with a real id, load every template with the console open, add only a host seen blocked and remove any that is never used. **Meta's list is unverified**: Meta's documentation says nothing about Content Security Policy (checked 2026-10-23); the hosts come from community and vendor guides.
- **The two wildcard exceptions, needing the project owner's written approval; not given.** The rule below says "never a wildcard host". Two wildcards are used on purpose, each limited to one Google-operated, analytics-only registrable domain and to `img-src` and `connect-src` only: `https://*.google-analytics.com` (regional collectors such as `region1.google-analytics.com`; an exact list would silently lose data) and `https://*.analytics.google.com`. Until the owner accepts the exception in writing it is proposed, not approved, and **an id should not be set in production** before that decision. A test asserts that these two are the only wildcards that can appear, that none is in `script-src`, `default-src` or `frame-src`, and that `https://*.google.com` never appears.
- **Nonce, no inline.** Provider scripts are added with the page nonce and only from `https://www.googletagmanager.com` or `https://connect.facebook.net` (the script loader refuses any other origin before an element exists). No `'unsafe-inline'`, no `'unsafe-eval'`, no bare `*` in `script-src` (tested). No Subresource Integrity: both vendors serve these files at fixed, unversioned addresses that change without notice, so a pinned hash would break them; the compensating controls are the origin allow-list, per-id hosts, consent and idle gating and the nonce (review I-2, accepted). If `script-src-elem` is ever added to a policy, the provider script hosts must be added there too.
- **Report-only and enforced get the same provider hosts.** Both are built from the same `analyticsCspHosts` function, so a host is never present in one and missing from the other. Hydrogen's enforced policy is unchanged otherwise: naming `script-src` or `img-src` replaces Hydrogen's `default-src` fallback (self, nonce, `cdn.shopify.com`, `shopify.com`), so `enforcedCspExtras` repeats those Shopify sources and adds only the provider hosts; `connect-src` is merged by Hydrogen, so only the new hosts go in. With no id set it returns nothing. The two policies still differ in everything else as described above (the report-only one is tighter; for example its `script-src` omits `shopify.com`), so a clean report-only run is the check that the enforced policy will not block a provider. Tested for the extras; **not observed** in a browser or on a production build behind a proxy.
- **The provider code is a lazy chunk.** The consent layer, the adapters and the script loader are one chunk, `ConsentRuntime`, requested after hydration and when the browser is idle, and only when an id is set ([ARCHITECTURE](../architecture/ARCHITECTURE.md) section 4b). It is a same-origin script covered by `'self'` and the nonce policy; it needs no new host. A failed chunk download hides the consent layer and nothing else.
- **Going from report-only to enforced for a provider** follows "Promotion to enforced" above, plus: a real id on staging, no `[Report Only]` message on any template, and the owner's written decision on the wildcards.

### Rule for adding any other provider

To add a provider (analytics, Meta pixel, Klaviyo, Judge.me, Shopify Inbox, a map tile server, Affirm):

1. The task that adds it (P7-01 to P7-03, P6-xx) names the exact hosts the vendor documents, and the directive each belongs in (`script-src`, `connect-src`, `img-src`, `frame-src`...). Never a wildcard host (the one exception is the pair of Google analytics wildcards in the bullet above, a proposal that stays unapproved until the owner accepts it in writing, DEC-093 and B-32, and that no environment may enable by setting the GA4 id before then) and never `'unsafe-inline'` or `'unsafe-eval'` for scripts; use the nonce.
2. The origin goes into `security-headers.ts` for the report-only policy first, with a test, and into the enforced policy only after the promotion steps above.
3. The script loads after consent or interaction (NFR-011), with Subresource Integrity where the vendor publishes a stable file, and sends no ZIP or e-mail unhashed.
4. Record the provider, hosts and reason in `progress/DECISIONS.md`; remove the origin in the same change that removes the provider.
5. A provider that needs `frame-src` also needs `frame-ancestors`/COOP reconsidered (`same-origin-allow-popups` is already chosen for popups).

## Third-party policy: live chat (P7-03, T-10; added 2026-10-26)

**Update 2026-10-28, tawk.to:** the host table now has one entry, for `PUBLIC_CHAT_PROVIDER=tawk`: `script-src https://*.tawk.to`; `connect-src https://*.tawk.to wss://*.tawk.to`; `frame-src https://*.tawk.to`; `img-src https://*.tawk.to https://tawk.link`, in both policies. Source: tawk.to help centre, "Resolving Content Security Policy (CSP) issues blocking the widget, images, and Knowledge Base articles" (https://help.tawk.to/article/why-are-images-not-showing-up-in-the-widget), read 2026-10-28. **Wildcard exception:** tawk.to documents only `*.tawk.to`, so this breaks the no-wildcard rule; it needs the owner's written approval before any environment sets the variable. Deliberately not added though the article lists them: `cdn.jsdelivr.net`, `s3.amazonaws.com`, Google Fonts hosts, `style-src`, `font-src`, `form-action`. Add a host only when report-only shows it blocked. Never seen in a browser.

**Default: no chat origin, and today none can be added.** The host table for a chat provider is `storefront/app/lib/chat/hosts.ts` and it is **empty until a provider is approved**: the only provider that runs is a development-only fake that loads nothing external, and Shopify Inbox (the default named in REQ-ANL-004) is BLOCKED and UNVERIFIED for this storefront and is refused at startup (`docs/integrations/CHAT.md`; no host, script address or CSP guidance exists in Shopify's documentation, and the one script address found is from an unofficial source and was not used). With `PUBLIC_CHAT_PROVIDER` unset, or with any provider that has no hosts, both policies are byte-for-byte unchanged (tested).

- **Wiring, in `entry.server.tsx` and `app/lib/security-headers.ts`:** `parseChatConfig`, then `chatCspHosts(providerId)`, then `enforcedCspExtras(analyticsCsp, chatCsp)` for the enforced policy and `buildReportOnlyCsp({chat})` for the report-only one. **Report-only and enforced get the same chat hosts** (one table feeds both), tested with a synthetic provider.
- **`frame-src`:** both policies keep `'none'` unless a provider names a frame host. When one does, `frame-src` is the base sources plus the chat window's origin; the report-only policy uses the same base sources as the enforced one (`'self'`, the Shopify CDN, `shopify.com`) so a clean report-only run is a real check (code-review n3, `619db62`). Hydrogen merges `connect-src`, so only the new hosts go in; naming `script-src`, `img-src` or `frame-src` replaces the fallback, so the Shopify sources are repeated where a directive is named (the same rule as for analytics above).
- **Adding the first real provider** follows the rule above, plus: the vendor's documented script, connect, image and frame hosts with source URL and date in `hosts.ts`, an adapter that implements `unload` (a real adapter without `unload` is not accepted on a consent-gated store; DEC-121), a DECISIONS line, report-only first with a real sandbox and every template loaded with the console open, no wildcard host, no `'unsafe-inline'`, the nonce for the script, and `frame-ancestors`/COOP reconsidered if the widget needs a popup. **Not done for any provider; nothing about a real vendor's hosts is known.**
- **Consent:** chat loads only after the shopper allows the `analytics` category while `PUBLIC_CHAT_REQUIRES_CONSENT` is true (DEC-120); which category chat needs is a legal decision (Q-025). The consent decision does not change the headers.

## Where the headers are applied

`storefront/server.ts` is the single exit: every response (documents, `.data` requests, resource routes such as `/api/*` and `/webhooks/*`, redirects from `storefrontRedirect` and the 500 error response) passes through `withSecurityHeaders` (`app/lib/security-headers.ts`), which copies a response whose headers are immutable (`Response.redirect()`, a proxied `fetch`) before writing. The headers go on **before** the pending session cookie is appended (`finishResponse` in `app/lib/server-safety.ts`), so a response with immutable headers and a pending session is copied first and cannot throw into the 500 path. `entry.server.tsx` adds what only a document needs (the two CSPs with the nonce, the charset, the canonical `Link`) and repeats the base set for `.data` requests as a safety net. **An own-server entry (Q-003) that does not use `server.ts` must make the same `withSecurityHeaders` call on every response**, or only documents and data requests are covered. Tests cover the immutable-headers copy and `finishResponse` with an immutable response and a pending session; the `server.ts` wiring itself runs only on a built server (verified with a request to `/api/extend/offers` on the dev server).

## Shopify's blocked telemetry (decision DEC-045)

Shopify's consent script (loaded from `cdn.shopify.com` by Hydrogen's analytics) posts performance telemetry to `otlp-http-production.shopifysvc.com`, which neither Hydrogen's enforced `connect-src` nor ours allows. Blocking it is **intended**: nothing we ship depends on it and it is a third-party origin (T-10). The e2e helpers (`tests/e2e/helpers/telemetry-refusal.ts`, unit-tested) ignore a console line only when it is a Content Security Policy refusal whose **blocked URL** is an https URL with exactly that host name (read from the quoted URL in Chromium's message; a longer host such as `<that host>.attacker.example`, the host in a query string, path or user-info part, or only in the policy text, does not count); a violation naming any other host (including in `[Report Only]` form) fails the specs.

## Known gaps

- With an analytics id set, Shopify's own consent telemetry is still blocked on purpose (DEC-045), and the provider hosts above are unverified against real traffic (Google's three connect hosts, all of Meta's list).
- `powered-by: Shopify, Hydrogen` is added by Hydrogen after our code runs; remove it with `poweredByHeader: false` in `createRequestHandler` options (server.ts) if the client wants it gone.
- Behaviour behind a real proxy (`X-Forwarded-Proto`, P-L5) and on a production build is unverified.
- Chat (2026-10-26): the chat host table is empty and no real provider is approved, so no chat header behaviour has been seen in a browser; the plumbing is unit-tested only, and the chat range has no security review.
