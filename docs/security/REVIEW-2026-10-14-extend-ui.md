## Gate verdict

**PASS WITH CONDITIONS (proposed).** No High. The browser-to-server contract for protection is tight: only a variant or line id and a plan key cross it, the server re-quotes, derives the price-point variant, attributes, parent and quantity, and the gate runs again after every change and at hand-off. ## Findings

### High
None.

### Medium

**N-M1. The offers budget does not bound Extend calls: quantity cycling defeats both the memo and the limiter (T-13; remainder of E-M2).**
Evidence: `offers-endpoint.ts:103-106` and `parseQuantity` accept `quantity` 1 to 99 from the browser on GET and POST; `offers-service.ts` `signature()` puts `item.quantity` in the memo key (comment says it stays on purpose) and the memo holds 200 entries; `createDistinctVariantLimiter` is keyed by variant id only. A known variant already in the window "always passes" (`offers-endpoint.ts` limiter comment), so one real variant with 99 quantities, repeated across 60 real variants, is about 5,900 distinct Extend questions per minute per isolate, and the 200-entry memo evicts them so repeats miss too. The same applies to the `quantity` of `CustomAddWithProtection` (1 to 99) through `resolvePlan`, which uses no limiter. The Sec-Fetch guard only stops cross-site browsers; curl sends no header.
Impact: Extend request volume and cost, latency; no price effect (the quote is checked against Shopify variant prices), no data leak. The circuit breaker trips only on failures.
Fix: for the offers GET/POST always quote at quantity 1 (the panel sends 1; confirm with Extend that price bands depend on price, not quantity) or ignore the browser quantity; count `(variantId, quantity)` in the limiter; host rate limit by IP at Q-003. Due: before the route is on a public staging URL.

### Low

**N-L1. With Extend off or misconfigured, coverage is recognised by title only (T-06; narrows the E-M1 closure).** `extend-seam.ts:222-227` `isPricePointByName` reads `merchandise.title` and `product.title`; the cart fragment (`lib/fragments.ts`) has no `sku`, while the catalog read recognises SKU, variant title and product title (`coverage-catalog.ts` `pricePointName`). A price-point variant whose pattern lives only in the SKU is recognised with Extend on (catalog) and not with Extend off (no catalog read), so it would stay as an ordinary line. Extend's own naming on a real store is unverified (V-16). Fix: add `sku` to the cart line merchandise fragment and to `isPricePointByName`; add a test with a SKU-only name. The admin guide already tells staff to name the products and never put them in collections.

**N-L2. The distinct-variant limiter is global per isolate, not per client (T-13).** Anyone can spend the 60-variant budget with 60 real variant ids (the catalog is public) and the panel then hides plans for other variants for up to 60 s. Fails safe (no cart or checkout effect: the gate and the add action do not use the limiter). Fix with the host rate limit (Q-003); until then accept.

**N-L3. Detective check: log-only, unverified, coverage not judged in two sync modes (T-02, E-M3).** Evidence: `webhook-processor.ts` `logDetectiveResult` emits `detective.violation` events and nothing else (no order tag, no notification); it runs only for `report` and `update` intents; `detect.ts` skips coverage lines (`isCoverageOrderLine`) because the Extend cross-check (`orders.ts`) judges them, and that runs only when `EXTEND_ORDER_SYNC=self`, so with `off` or `extend-app` a cheap price-point SKU or a forged plan id is judged by nobody. Delivery method comes from the shopper-writable `delivery_choice` attribute (the ZIP check uses the shipping address, which is the right authority). `shippingAddress` and the Order read assume V-20 (attribute copied to the order, null address for pickup) and Shopify's protected-customer-data approval for address fields; neither was seen on a real order. Fix: wire the findings to something staff see (Flow tag or email per the RUNBOOKS entry) and test it on a development-store order; judge coverage price versus plan in the detective path or state in the runbook that `self` mode is required for it; run `scripts/detective/report.mjs` once against a development store (V-20) before any real order. The owner's written acceptance of ADR-0006 is still needed.

**N-L4. E-L9 template items still open.** `server.ts` still uses `response.headers.set('Set-Cookie', ...)` when the session is pending (drops the cart or ZIP cookie on that response; only when a customer-account session changes) and still `console.error(error)` with the raw error. Fix: `append`, and log `error.message` only.

**N-L5. Dev-only header observation.** Cart and delivery POST responses show `Vary: Origin` (Vite) and `private, no-store` without `Vary: Cookie`. No-store makes that safe; confirm on the real host that no CDN rule overrides `private` or `no-store` (see ZIP section).

## Verified

**Protection actions (T-01, T-02, T-06), code plus tests plus live.** Live (flag off, bedding.mock.shop, throwaway cart): `CustomAddWithProtection` with extra `coverageVariantId` and `price` fields, `CustomAddProtection` with a foreign line id, and a plan key containing spaces and `<script>` each got 400 and changed nothing; a foreign Origin got 400; all responses `private, no-store`. Not driven live: the success path and everything needing the flag on (mock.shop has no price points, no `nodes(ids)`, no nested lines: V-16, V-02). Reasoning on the hostile cases you listed, each backed by a named test unless noted:
- Forged plan key: `validateAddWithProtection` and `parseProtectionCommand` accept a plausible id only; `resolvePlan` and `addProtectionToLine` look it up in the server's own quote, else `protection-plan-unknown` (tests "a forged plan key or line carries a known code back to the step and changes nothing").
- Coverage variant sent as the item: `resolvePlan` refuses when the id is in the catalog's coverage set (`protection-not-allowed`); `coverageItemFor` returns null for it; test "a coverage variant named as the item".
- Quantity, parent, price, attributes injection: only three fields are read; the coverage quantity is the item quantity (new) or `min(quantity, uncovered)` (existing); browser attribute keys must not start with an underscore (`PROPERTY_KEY`), so `_extend_*` can only come from the server; a plain `LinesAdd` of a coverage variant has no parent and the gate removes it as an orphan.
- Another cart's line: `addProtectionToLine` finds the line in the server's own cart read and requires it in the engine's own `accidentProtection.lines`; an id from elsewhere gives `protection-not-offered` (live: foreign line id gave 400).
- Gift, haul-away or protector as the covered line: only `regular` lines are offered; `evaluateAccidentProtection` removes coverage whose parent is not regular; test "removes coverage nested under a free gift".
- Plan key replay at a different price after a size swap: the coverage price is always taken from a fresh quote for the line's current price, and the gate removes a coverage line whose Shopify price is not in the plans quoted for its parent (`coverage-price-mismatch`); test "after a size swap from a low to a high size the old coverage is removed". A key that is not in the new quote is refused.
- Ordering races (add then change size): every cart request ends with `revalidateCartOffers` after its own mutation, and `/checkout-steps` repeats it at hand-off; corrections only lower or remove, so the last gate to run sees the final state. A gate that fails inside the cart action is swallowed by design, the hand-off gate covers it. Worst case is lost coverage (safe direction). Not run as a concurrent live test (needs the flag on and a store).
- Declining via a forged step: `declineProtection` revalidates and requires the step pending with lines; `clearEarlierDecline` runs before any add; tests "a forged decline for a cart where nothing is offered writes nothing". The attribute only feeds order notes.
- Flag-off cart holding coverage: `extend-seam.ts:268-290` removes every recognised coverage line (`NOTHING_ELIGIBLE` makes every parent ineligible), with no network call; test "flag off: nothing is added" and extend-wiring tests. Recognition limit: N-L1.
- Unjudged lines: lines beyond the quote cap get an empty allowed-price list, so their coverage is removed (`protection.ts`, test "more sizes than one quote can ask about").

**Offers route (T-13).** Fabricated ids are not charged to the budget (`answerOffers` filters to variants Shopify returned; test "an attacker looping fabricated ids burns no budget"); the Sec-Fetch guard refuses `cross-site` on GET and POST (`isSameSiteFetch`, absent header passes by design); POST bodies are cut off at 4 KB while streaming; cart, delivery and checkout-step forms now use `readSmallForm` (cap on declared and streamed bytes). Residual: N-M1, N-L2.

**Root headers and delivery seed (T-05, T-08).** Live: `GET /`, `/collections/all`, the 404 page and the root data request (`/_root.data`) all return `Cache-Control: private, no-cache` and `Vary: Cookie`; `/delivery` and cart POSTs return `private, no-store`; the ZIP-saving response sets `delivery_zip` with `HttpOnly; SameSite=Lax; Max-Age=2592000; Path=/` (Secure follows the host, omitted on localhost). a route that exports no `headers` inherits the root's (React Router `getDocumentHeaders`, confirmed in the library source); every route exporting `headers` (cart, cart permalink, checkout-steps, delivery, account, stores, discount) uses no-store or the private set; the only public `max-age` responses are robots and sitemaps, which have no root loader. With the cookie set the ZIP appears in the HTML and in the data response (2 and 1 occurrences) and with no cookie 0; neither contains the raw cookie value or a secret; 0 occurrences of the ZIP in the dev server log. The ZIP is location data: it is in a private, cookie-varied response only, never a URL, log, Storefront cache key or third-party script (Analytics gets shop and cart data only). Residual: private responses may sit in the browser's own cache and back-forward cache (acceptable; shared computers), and a CDN rule that overrides `private` would leak one shopper's ZIP to another: test on the chosen host (Q-003): two requests with different cookies, compare, and read the cache-status header. The ZIP should be named as personal data in the privacy policy (T-16).

**Secrets logging (T-04, T-05).** `cookie-secret.ts` logs only the variable name, once per isolate; `context.ts` throws a message naming the variable and the 32-character rule, never the value; production refuses to serve with a short `SESSION_SECRET`. Dev log from this session held no secret or ZIP. Webhook shop-domain check (E-L2b) compares only for `*.myshopify.com` and logs at error level.

**Detective code and script (T-05, T-02).** Logs carry order id, status, violation code, unjudged reason and line ids only; a result type has no field for a name, address or ZIP; the shipping ZIP and country are read to answer yes or no (`admin-order.ts` query asks `countryCodeV2 zip` only). Unreadable, truncated or unknown shapes are reported unjudged, never clean; a missing or invalid rule configuration is reported for every order. `report.mjs` is read-only (client without mutation rights), needs `SHOPIFY_ALLOWED_STORES`, takes the token from the environment and redacts it in logs, validates `--since` and `--limit`, writes `--out` with `wx` (never overwrites), prints ids and codes. 13 script tests pass.

Partly: E-M2 (N-M1, N-L2); E-M3 (detective built, N-L3); E-L8 (`.env.example` now demands a separate read-only token; scope cannot be checked from here); E-L9 (EXTEND.md text reconciled, `server.ts` items open: N-L4).
