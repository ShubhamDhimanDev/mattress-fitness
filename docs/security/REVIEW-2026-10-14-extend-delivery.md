# Security review: Extend webhook, offers route, delivery ZIP and haul-away steps, commit 1173d79

Reviewer: security-engineer. Date: 2026-10-14. Scope: commit `1173d79` on `feat/foundation-libs-and-shell`: `routes/webhooks.shopify.tsx`, `app/lib/extend/{webhook,webhook-handler,webhook-processor,replay-store,order-coalescer,admin-client,admin-order,config,env,runtime,offers-endpoint,offers-service,coverage-catalog,coverage-facts}.ts`, `routes/api.extend.offers.tsx`, `offers-runtime/{extend-seam,server,runtime}.ts`, `delivery-runtime/*`, `routes/delivery.tsx`, `routes/checkout-steps.tsx`, `scripts/extend/reconcile.mjs`. Threats: T-03, T-01, T-02, T-05, T-06, T-13 (plus T-04, T-07, T-08 where touched). Uncommitted layout, home and brand files were ignored. Other agents were editing source during this review (the working tree grew from 19 to 34 modified files), so line numbers refer to `1173d79`.

Method: code reading; 60 Vitest files (2,483 tests, webhook, extend, offers-runtime, routes) all pass; dev server on port 3900 (bedding.mock.shop, throwaway secrets in a scratch env file outside the repo, no `.env` file read) with hostile requests; a throwaway Vitest probe of `parseExtendHost`, `parseExtendConfig` and `adminConfigFromEnv` with 34 hostile hosts; fresh `npm run build` and grep of `dist/client` (92 JS files); `npm audit --omit=dev`; diff and history secret scan. The dev server was stopped (port 3900 verified free). No source file changed. No secret value is written here.

## Gate verdict

**PASS WITH CONDITIONS (proposed).** No High. The webhook receiver is sound: signature on raw bytes, constant time, no information leak, size caps, bounded work per order. The delivery cookie cannot be forged into anything the shopper could not set freely. Two Medium findings (E-M1 coverage recognition off when Extend is off or misconfigured, E-M2 unauthenticated offers GET with no rate limit) and the haul-away ZIP gap (E-M3) must close at the stated points. H-1 (react-router advisories, ADR-0008) is unchanged and still needs the owner's written acceptance before production.

## Findings

### High

None.

### Medium

**E-M1. Coverage lines are unmanaged whenever Extend is off or misconfigured (T-06, T-02; reopens O-M2 in that state).**
Evidence: `extend-seam.ts:176-178` returns `NO_EXTEND_INPUTS` when `offersConfigOf(runtime).status !== 'enabled'` (flag not exactly `true`, missing credential, `invalid_host`, bad token). The name check `isPricePointByName` (line 154) and the catalog read are skipped too, and nothing is logged for the `disabled` outcome. With empty `coverageVariantIds`, `withCoverageRoles` assigns no coverage role and `protection.ts` never runs.
Scenario: the price-point products exist in the store (they must be published to the headless channel, ADR-0009), the flag is off (the documented NFR-013 kill switch) or one Extend variable is mistyped. A coverage variant can then be added alone, or under a gift, through our own `/cart` and reaches checkout. The shopper pays for protection with no covered item and no contract (customer harm, invoicing error).
Fix: recognise coverage by the catalog tag and by name regardless of the Extend flag or credentials (no Extend call is needed for that); with Extend off, treat every coverage line as an orphan and remove it. Log `coverage.inputs_degraded` when the config is `disabled` for a reason other than `flag_off`. The code review's "catalog-read failure fails open" finding is the same family: confirmed Medium (the name fallback covers only lines already in the cart, and only while Extend is enabled). Due: before any price-point product exists in a store that takes orders.

**E-M2. Offers route is an unauthenticated, unthrottled proxy to Shopify and Extend (T-13).**
Evidence: `api.extend.offers.tsx:38-40` GET loader has no origin or rate check; POST only checks Origin (line 47). Live: 40 sequential GETs with distinct variant ids and quantities took 16.5 s (about 330 ms each, i.e. one uncached Storefront facts query each: `coverage-facts.ts:140` keys the cache on the ids). The Extend memo key (`offers-service.ts:149-157`) includes quantity (1 to 99) and is capped at 200 entries, so cycling product and quantity defeats it and each miss is one Extend call (the circuit breaker only trips on failures). A cross-site `<img>` can trigger GETs from visitors' browsers.
Impact: Storefront API quota, Extend request volume and cost, latency for real shoppers. No data leak and no price effect (the answer carries only plans).
Fix: rate limit by IP at the host (needs Q-003); drop `quantity` from the memo key or bucket it (Extend price bands depend on price, not on quantity: confirm with Extend), raise the memo cap; require `Sec-Fetch-Site: same-origin` when present on GET; also cap the POST body by streaming (below, E-L4). Due: before the route is enabled on a public staging URL.

**E-M3. Haul-away eligibility rests on a ZIP the shopper types, not on the delivery address (T-02).**
Evidence: `zip-cookie.ts:3-6` (the comment says so), `steps.ts:48-61`, `haul-away.ts` eligibility uses `runtime.zip`; the detective note is `TODO(P5B-05)` at `webhook-processor.ts:88`. The ZIP cookie signature proves only that the server wrote it, and anyone can obtain a signature for any ZIP from `POST /delivery`.
Scenario: a shopper saves an in-zone ZIP, accepts in-home delivery and haul-away, then enters an out-of-zone shipping address in Shopify checkout. Our server cannot see that address; ADR-0006 and ADR-0007 accept this only if a post-order check exists, and it does not yet.
Fix: build P5B-05 (shipping ZIP versus zone on `orders/paid`, independent of the Extend sync mode, yes/no result logged, never the ZIP) and enable a Shopify delivery-zone restriction at checkout (Local delivery rules) as the real control. The owner must accept the residual in writing (ADR-0006 wording). Due: phase 5B gate. Carries review M-4.

### Low

**E-L1. `SESSION_SECRET` is reused for the delivery cookie, with no domain separation and no strength check (T-04).**
Evidence: `zip-cookie.ts:22-33` uses `SESSION_SECRET`; `context.ts:39` only checks it is non-empty; DEPLOYMENT.md says "generated by us". React Router's cookie signature is HMAC-SHA256 over the base64 payload only (live: `delivery_zip=IjYwNjQ1Ig%3D%3D.<43-char tag>`, payload `"60645"`): the cookie name is not part of the signed data. Consequences: (1) `POST /delivery` is a free signing oracle for 100,000 known plaintexts under the same key that signs the Hydrogen session cookie (which can hold customer-account tokens), so a weak secret becomes an offline dictionary attack from one anonymous request; (2) a signed ZIP value is a valid signed value for any other cookie using that key. Live: a signed ZIP replayed as `session=` caused no error or privilege (`/` 200, `/account` 302 as for an anonymous visitor), and a signed session replayed as `delivery_zip` is rejected by `parseZip`, so no exploit today.
Fix: add a separate `DELIVERY_COOKIE_SECRET` (or derive a key per purpose) and require at least 32 random characters for every cookie secret at startup (`openssl rand -hex 32` in DEPLOYMENT.md).

**E-L2. Header spoofing in the webhook (T-03), accepted by design, with two details.** `X-Shopify-Triggered-At`, `X-Shopify-Webhook-Id` and `X-Shopify-Topic` are not signed. Live: one validly signed body replayed with fresh ids and fresh timestamps is accepted every time (200), and a stale timestamp is acknowledged and ignored (200), so an attacker who captured one body defeats id and age checks; the bound is the per-order coalescer (one sync per order per 10 s, 3 runs per chain; unit test "a flood of fresh webhook ids for ONE order costs at most two syncs") plus the idempotent PUT. The capture needs the signed body, which only Shopify, a TLS break or a log leak provides. Details: (a) swapping the topic header on a signed `refunds/create` body makes `routeShopifyTopic` read the refund `id` as an order id (`webhook.ts:183`) and re-sync an unrelated order id if one exists: harmless but unintended; take the order id from the topic the payload shape proves, or ignore topic and use only `order_id ?? id` after checking the shape; (b) check `X-Shopify-Shop-Domain` against `PUBLIC_STORE_DOMAIN` as defence in depth if the app is ever distributed (the Admin read already uses only our own shop).

**E-L3. Missing `X-Shopify-Triggered-At` returns 400 (availability), code review finding.** `webhook.ts:285-295`. Shopify documents the header on every delivery, so a 400 is unlikely in production, but a 400 makes Shopify retry and, after repeated failures, delete the subscription. Confirmed Low. Fix: treat a missing header as "no age check" after the signature has verified (the idempotent sync and coalescer are the real bounds), keep rejecting a present but malformed or future value.

**E-L4. Unbounded request bodies on `/delivery`, `/checkout-steps`, `/api/extend/offers` (T-13), code review finding.** `delivery.tsx:82` and `checkout-steps.tsx:206` call `request.formData()` with no cap; `offers-endpoint.ts:82-91` checks Content-Length only, then `request.text()` reads everything when the length is absent. Live: an 8 MB POST to `/delivery` gave 500 in 38 ms (the dev proxy resets large bodies, so this is not proof of the production behaviour). Confirmed Low (memory per request, no data effect), Medium if the host sets no body limit. Fix: reuse `readCappedBody` (`webhook-handler.ts:62`) with a small cap (for example 8 KB) before parsing, in all three places, and also set the limit at the host.

**E-L5. Reconcile `--resend --live` can send real order PII to the Extend demo host.** `reconcile.mjs:266` allows the demo host; the Shopify store only has to be in `SHOPIFY_ALLOWED_STORES`. If a live store is allow-listed, real names, emails, phones and addresses go to a sandbox environment. Code review finding, confirmed Low (operator-run, dry run default, production host refused). Fix: with a non-loopback host require the store to be a development store (explicit `--dev-store` acknowledgement or a separate allow-list), print the count of orders that will be sent before sending, and keep the allow-list to development stores.

**E-L6. `declineHaulAway` records a decline without checking that the step applies (T-02 data quality).** `steps.ts:105-118` checks only that the cart has lines. Live: a decline was accepted (302) on a cart where the step does not exist, and a decline can sit next to a haul-away line. The attribute only feeds customer-service notes. Fix: revalidate and require the haul-away step to be pending, as `acceptHaulAway` does.

**E-L7. Production-safe defaults depend on callers (T-03/T-04 hardening).** `parseExtendConfig` allows the loopback host unless `production: true` is passed (probe: default options accept `http://127.0.0.1:4010`). Every storefront caller passes `import.meta.env.PROD`, so production refuses loopback (probe: `invalid_host`), but a new caller that forgets the option fails open. Make loopback opt-in (`allowLoopback: true`) for the scripts and tests only.

**E-L8. Admin token scope and sharing (T-04).** The storefront runtime now holds `SHOPIFY_ADMIN_API_ACCESS_TOKEN` (`admin-client.ts:41`), and `.env.example` shares the name with the local scripts, which write. If one token serves both, a compromised storefront process can write to the store. Fix: a dedicated read-only-orders token for the storefront deployment (scope `read_orders` only; `read_all_orders` only if reconcile needs older orders), a separate token for scripts, and say so in DEPLOYMENT.md.

**E-L9. Smaller items.** Session commit overwrites other cookies: `server.ts` sets `Set-Cookie` with `headers.set` when the session is pending, which would drop the cart or ZIP cookie on that response (template code, only when a customer-account session changes). `console.error(error)` in `server.ts` still prints raw errors (O-L7 carried). `EXTEND.md` section 7 says a durable replay store is needed while the ADR-0009 addendum says best effort is enough, and section 8 still says `server.ts` is not wired to the seam (it is): reconcile the text. The 503 for a missing webhook secret reveals configuration state to an unauthenticated caller (acceptable, and it is what makes a missing secret loud). Zone probing: `/delivery` tells anyone which ZIPs are in the zone (public marketing information).

### Code review findings not re-rated above

"Coverage price not checked against the parent" and "second same-product line loses coverage": business-logic defects in coverage linking and the Extend quote (`offers-service.ts:133-147`, quote per product id), no security impact beyond T-06 customer harm; re-rate Low from a security view, and the first one (a cheap coverage variant attached to a dear item) is also what the sync cross-check flags after the order (ADR-0009 item 7). The review's own fixes are in progress and were not reviewed.

## Verified

**T-03 webhook (live, dev server, throwaway secret).** Results: GET 405 with `Allow: POST`; no, wrong, empty, hex-encoded or other-body signature each 401 with an empty body and `Cache-Control: no-store`; correctly signed body 200 with no body; tampered body 401; future timestamp (+1 h), garbage timestamp, short or injected webhook id each 400; stale timestamp (-7 h) 200 ignored; unsupported topic 200 ignored; malformed JSON or payload 400 after the signature check; declared 5 MB+ Content-Length 413 before buffering (the second run hit a dev-proxy connection reset; unit tests `refuses a declared Content-Length over the cap`, `cuts off a streamed body at the cap` cover the streamed case, which the dev proxy cannot send). Timing: 300 interleaved requests each with an all-wrong, a first-42-characters-right and a one-character signature gave medians of 18.3, 18.1 and 17.7 ms (indistinguishable; `webhook.ts:53-62` compares the full length with no early exit). Missing secret: unit test gives 503 with the variable name logged, never the value; empty secret refused. Logs for 40+ requests hold only event, reason, order id and topic: no body, header, email (the test body carried one) or secret; the dev server prints variable names only.
**Admin read and Extend host (SSRF).** `parseExtendHost` probe, 34 inputs: accepted only `https://api.helloextend.com` and `https://api-demo.helloextend.com` (with port 443, case folding, trailing slash or surrounding spaces normalised to the origin), refused userinfo, `@` and backslash tricks, suffix hosts, other ports, http, paths, query, fragment, trailing dot, encoded dots, metadata IP, file and ftp. Loopback forms (including `127.1`, decimal and hex IPs, `[::1]`) pass only with `allowLoopback`; in production mode `invalid_host` (E-L7 for the default). `adminConfigFromEnv`: only `<shop>.myshopify.com` (14 hostile variants refused, CRLF token refused); the shop comes from `PUBLIC_STORE_DOMAIN`, never from a header; `redirect: 'error'`, 8 s timeout, 2 MB cap, 3 attempts with backoff. The token is in a closure (`JSON.stringify` of the config does not contain it).
**Secrets and bundle (T-04).** Fresh build: `dist/client` (92 JS files) has 0 hits for `SHOPIFY_APP_CLIENT_SECRET`, `SHOPIFY_ADMIN_API_ACCESS_TOKEN`, `EXTEND_ACCESS_TOKEN`, `EXTEND_API_HOST`, `EXTEND_STORE_ID`, `EXTEND_ORDER_SYNC`, `SESSION_SECRET`, `OFFER_CONFIG_JSON`, `X-Extend-Access-Token`, `X-Shopify-Hmac`, `verifyShopifyWebhook`, `handleShopifyWebhook`, `processOrderAction`, `readOrderForSync`, `adminConfigFromEnv`, `parseExtendHost`, `answerOffers`, `loadCoverageCatalog`, `extend-coverage`, `saveDeliveryZipHeader`, `readDeliveryZip`, `delivery_zip`, `PRIVATE_STOREFRONT`. Commit diff scan: only fixtures named `...-not-real`. Only `.env.example` is tracked or ever added in history; `storefront/.env*` are git-ignored.
**Delivery cookie (T-08, T-05).** Flags: `HttpOnly; SameSite=Lax; Max-Age=2592000; Path=/` (`Secure` omitted on localhost by design, from the host as for the cart cookie, carried O-L9). Forged cases all read as "no ZIP": unsigned bare value, unsigned base64 payload, payload changed under an old tag, tag from another key. Validation: 9 ZIP shapes; fullwidth and Arabic-Indic digits refused, whitespace trimmed, ZIP+4 reduced to 5, over-length and control characters refused, only the clean 5 digits are stored. Responses carry `private, no-store`. The ZIP never appears in a URL, log (0 hits for the ZIPs used) or the client bundle; the product page fetches it after load from `/delivery`.
**CSRF and origin.** Cross-origin `Origin` and `Origin: null` on `POST /delivery` and `/checkout-steps` got 400 from React Router's own check before ours ran (as in the previous review); `/api/extend/offers` POST with a foreign Origin got our 403; same-origin and no-Origin pass (Lax covers the latter). The dev `Access-Control-Allow-Origin` header comes from Vite and does not exist in a production build (not verified on a host).
**Offers route input.** 400 for no id, two ids, quantity 100, `1e2`, a non-variant GID, an injection-shaped id, 11 items, a body over 4,096 characters, bad JSON, `items` not an array; 405 for PUT and DELETE; extra query keys (`price`, `planId`) and `__proto__` keys ignored; answers `private, no-store`; no CORS headers from the app. Prices, product ids and categories come from Shopify; plan links are https-only (`offers.ts:141-152`).
**Step forgery (live, throwaway cart).** `haul-away accept` with pieces 999, -1, `1e3`, and extra `variant` and `price` fields, and `delivery-choice` with `in-home` and `pickup` (no haul-away rule configured), all redirected with fixed error codes and changed nothing; an unknown step, a path-traversal choice and a foreign Origin got 400. Server logic (read): the variant and cap come from the rules, `clampHaulAwayQuantity` maps NaN to 0 (`step-command.ts:41` accepts 1 to 3 digits only), in-home needs an in-zone ZIP and a pending question (`choice-step.ts` `mayChoose` judges without the recorded answer), the decline is cleared before the add so a failed add leaves no service line beside a decline, a second accept is refused when pieces are already in the cart. Covered by `delivery-steps.test.ts` and `delivery-routes.test.ts` against fakes; mock.shop cannot answer `nodes(ids)`, so the success path was not driven live.
**Reconcile script.** Read-only by default; any store contact needs `SHOPIFY_ALLOWED_STORES`; `--resend` needs `--live`, an allow-listed store and a loopback or demo host (production refused, `reconcile.mjs:266`); `--since` and `--limit` validated before use in the query; output holds ids and fixed reasons (plan ids pass `isPlausiblePlanId`, so no control characters); the mock source reads only a loopback host with `redirect: 'error'`. The mock binds to 127.0.0.1.
**Dependencies (T-12).** Commit changed no `package.json` or lockfile. `npm audit --omit=dev`: 7 findings (2 high: react-router, lodash; 4 moderate; 1 low), the same set as ADR-0008. H-1 unchanged.
