## Findings

### Medium

**RR-M1. No `handleError` export: the framework's default logger prints whole error objects, including GraphQL variables, and a stack trace for every refused POST (T-05, T-13)**

- Evidence: `grep handleError storefront/app` finds nothing, so React Router uses its default, which is `console.error(error)` for every error it handles itself (`node_modules/react-router/dist/development/chunk-S54KXAEJ.mjs:1162-1170`). This includes the CSRF refusal (`:1472-1476`, `handleError(e)` then a plain `400 Bad Request`; the single-fetch path at `:899-902` does the same) and any error thrown from a loader or action. Hydrogen builds its Storefront errors with a `cause` that holds the query text and `variables: JSON.stringify(queryVariables)` (`@shopify/hydrogen/dist/development/index.js:1738-1752`, `throwErrorWithGqlLink` `:1987-2007`); `console.error` prints the cause. Variables on this site include cart ids (a cart id carries its access key), search terms and handles. `server.ts:67-74` already redacts to the class name, but only for errors that reach its own `catch`; errors handled inside React Router never get there. The earlier fix N-L4 states this exact risk ("a message or cause of a failed Storefront call can hold the query, its variables and a cart id") and closes it for one path only.
- This is what F-3 saw (an unstructured stack trace per foreign-origin POST), but the larger exposure is the loader errors. Pre-existing, not introduced by the range; found while judging F-3. I did not trigger a failing loader to see the printed line, so the exact content is from code reading.
- Impact: cart access keys or search text in journald/log files (T-05); attacker-triggerable multi-line log entries that break the JSON-per-line convention the alerting relies on (the nginx general zone allows 20 requests a second per address).
- Fix (developer): export `handleError(error, {request})` from `app/entry.server.tsx` that skips `request.signal.aborted` and calls `logError('request.framework_error', {...errorFields(error), path: new URL(request.url).pathname, method: request.method})` (class name and path only; the logger's closed event vocabulary needs the new name in the RUNBOOKS list). Add a unit test with an error whose `cause` holds a cart id and assert the line contains neither. Optionally give a refused CSRF its own event (`request.csrf_refused`, no stack).

### Low

**RR-L1. Case variants of the 15 registry handles bypass the short-window rule (T-13; partial regression of the C-M2 fix)**

- Evidence: `pages.$handle.tsx:40-42` sets `alwaysLong: contentPageByHandle(handle) !== null`, and `contentPageByHandle` lower-cases its input (`content-pages.ts:186-190`). So `/pages/FAQ`, `/pages/fAq`, `/pages/FaQ` all get the long strategy. The cache key is the full variables, so each spelling is its own entry living 1 hour fresh plus up to 23 hours stale, whatever Shopify answers (a null page is cached too). Probe output: `FAQ:true:long fAq:true:long FaQ:true:long Faq:true:long`. `delivery-and-shipping` has about half a million spellings.
- Impact: the junk-entry pressure on the 500-entry stand-in cache that C-M2 described is still available, now restricted to registry-shaped URLs. It no longer touches the footer entry (that is memoised, see the closure table), so the effect is cache churn and more Storefront reads, the same as the pre-existing product and collection handles (T-13 Partial). Whether Shopify itself answers a differently cased handle is unverified.
- Fix: make the registry test exact, `alwaysLong: contentPageByHandle(handle)?.handle === handle`, and call `rememberFound` only when `page.handle === handle` (the query already returns `handle`). A differently cased request then starts short like any unknown handle. Add the four-spelling test.

**RR-L2. A hung Storefront call blocks every document request through the shared refresh (T-13 availability)**

- Evidence: `content-pages-data.ts:158-167`. `refresh ??= readAvailability(...).finally(...)`; every later caller returns that same promise, and nothing bounds it. The code does not set a fetch timeout on `storefront.query` (no `AbortSignal` or timeout anywhere in `lib/context.ts` or `server.ts`). Before the fix a hung call stalled only its own request; now one hung call stalls all of them, because the root loader awaits this value on every document (`root.tsx:140-147`). Node's HTTP client eventually gives up (about 300 seconds by default, not verified on the deployed Node), so the window is minutes, not forever; the comment's "never left running" argument covers cancellation, not slowness.
- Fix: race each caller against a short timer (3 to 5 seconds) and answer `memory?.value ?? NO_CONTENT` on timeout, leaving the shared refresh to finish by itself; a test with a never-settling `query` must resolve.

**RR-L3. During a Shopify failure every request retries and waits (T-13)**

- Evidence: on failure `readAvailability` returns the stale value but leaves `memory.at` unchanged (`:142-151`), so every request after the fresh minute starts a new attempt and waits for it (single-flight limits concurrency to one, not frequency); after the 10-minute stale limit the answer is `NO_CONTENT` and the retry per request continues. The unit test (`content-pages-data.test.ts:224-240`) pins this. Impact: slower pages while the query specifically fails (for example throttling or cost rejection), and extra load on a service that is already struggling.
- Fix: after a failure remember the time of the attempt and do not retry for 15 to 30 seconds (serve stale or empty meanwhile).

**RR-L4. The JSON-LD test reproduces the escape instead of using it (C-I1 only partly closed; T-07)**

- Evidence: `tests/unit/seo/content-pages-seo.test.ts:549-564` re-implements React Router's `escapeHtml` in the test (`ROUTER_ESCAPE`); the file comment says why (the component needs the framework context). The test therefore proves our data would be safe if the router escapes, not that it does. An upgrade that loses the escape (the pin is held, ADR-0008, and is due to be revisited) would still pass. The e2e specs parse `ld+json` text but never feed a `</script>` payload.
- Fix: one of (a) a unit test that renders the router's own `<Meta>` or `<Scripts>` helpers server-side, if the version allows it without a full framework context; (b) an e2e case against a fixture whose title contains `</script>`; (c) at least a test that fails when `react-router` is not 7.16.0, with the comment "re-run the JSON-LD escape check when this changes".

### Info

- **RR-I1 (CSRF 400 and the F-3 500).** Judgement on the question asked: low risk, no wrapper needed. `server.ts:77-86` is the single exit and calls `withSecurityHeaders` on every response, including the framework's plain `400 Bad Request` for a refused POST, so CSP, nosniff and the rest are present (in code; I did not curl it). A POST answer without `Cache-Control` is not stored by shared caches by default, and `X-Robots-Tag` has no meaning on a POST. The cost of the 400 is the log line (RR-M1), not the response. The intermittent 500 after it ("fetch failed, ECONNRESET", MiniOxygen) is on the dev tooling's worker connection; whether the production Node adapter shows it is unverified, and the `prodpreview` run suggested by QA is the right test. The RR check also depends on the `Host` header equal to the `Origin` host behind nginx (`proxy_set_header Host $host`, `deploy/nginx.conf.example:264`); a mismatch would refuse every real POST (cart, signup), which is the open item P-L5. Our own `isSameOriginRequest` is the second layer and runs only for requests RR let through.
- **RR-I2 (module memo of availability).** Cross-request state, but only derived data: sets of registry handles and booleans, the same for everyone, no cookie, ZIP, cart or URL input reaches it (`content-pages-data.ts:105-121`; the query has no shopper-specific variable). Country and language are fixed (US English), so no per-locale answer is mixed. The returned `Set`s are shared between requests: no consumer mutates them today (`contentPageTarget`, `policyRedirectFor`, `existingContentPaths` only read); freezing them would keep it that way. Memory is constant (three sets of at most 15 entries). On Oxygen or any Workers runtime, awaiting a promise started by another request can be cancelled when that request ends; the planned host is Node (owner decision 2026-10-23), so this matters only if Q-003 changes.
- **RR-I3 (stale-if-error and unpublishing).** The memo serves the last good answer for 10 minutes only when a refresh fails, so a link to a page that was unpublished can linger at most 60 seconds (normal) or 10 minutes (during an outage) in the footer, on top of the 1 hour Hydrogen cache the answer comes from. The page route itself is the longer exposure: a registry page body is cached for an hour fresh plus a stale window (pre-existing, T-13/T-07 design). For a legal take-down add one runbook line: the page can stay visible for up to an hour after unpublishing in Shopify, and a restart of the service clears the in-memory copies (own VPS).
- **RR-I4 (promotion logic, otherwise sound).** `known` holds handle keys only, is capped at 200 and cleared when full (`content-pages-cache.ts:14-32`), is the same for every shopper, and an entry is added only after Shopify returned a non-null page, blog or article, so an attacker cannot make junk handles long unless Shopify answers with content for them. The one way is a differently cased handle if Shopify's lookup is case-insensitive (the key is the typed spelling): each spelling of an existing page would be promoted. The RR-L1 fix (compare the returned `handle`) covers that too. Paged blog lists and the blog index use the short window when `cursor` is present, including an invalid cursor (served the first page), which is the safe direction.
- **RR-I5 (`cursorPaginationVariables`).** Shared by `collections._index` and `account.orders._index`. No authorization effect: the order query runs under the signed-in customer's token (`requireAccountSession` first), the cursor is only a position inside that customer's own list, and the value travels as a GraphQL variable. The new behaviour is that a cursor outside `CURSOR_PATTERN` (`[A-Za-z0-9+/=_.~:-]{1,512}`) silently shows page one. I could not verify the character set of Customer Account API cursors; if one contains another character, "Load more" would loop on the first page. Worth one check on the development store.
- **RR-I6 (banner privacy link and header default).** `privacyPath` is `footerPages.find(id === 'page:privacy-policy')?.to` (`root.tsx:165-166`); `to` comes only from `contentPageTarget`/`footerPageLinks` (constants in the registry: `/pages/<handle>` or the policy path), never from the URL, a cookie or Shopify text. No open redirect and no `javascript:` path; null hides the link. The signup `privacyHref` is derived the same way. The fixed navigation default (`MAIN_NAV`) holds no Shopify-written link; `buildFallbackNav` adds them only for pages found.
- **RR-I7 (root `signup` field).** `{sms: boolean, privacyHref}` or `null` (`config.ts:82-89`), in every page's data. It tells a visitor that signup is configured and whether SMS is on; no key, list id or env value.
- **RR-I8 (shouldRevalidate exception).** `root.tsx:61` skips revalidation only when `formAction` is `/signup`, which the page itself sets on its form; a visitor cannot change what other forms revalidate. The signup action reads and writes no session, cart or cookie (`signup.tsx:40-50`, the handler never touches `context.session`), so no auth state can go stale; the answer carries no `Set-Cookie`. The `.split('?')[0]` handles a query string. A post to a different path still revalidates (`:64`).
- **RR-I9 (limits and counters).** The limits are now `overall` 60 per 15 minutes, per address 6 per 15 minutes and 20 per day (shared bucket 60 and 100 when no trusted address header), per mailbox 3 per hour and 5 per day, per number 2 per day (`limiter.ts:51-60`). The ceiling this leaves is 5,760 attempts a day through the overall counter (about 240 an hour), each possibly a confirmation mail to a stranger: smaller than before (1,200 per hour), still not zero; keep it on the list of what the owner accepts. The in-memory store keeps at most 5,000 keys per scope; the daily mailbox scope could in principle reach that at the overall ceiling (5,760), which would let the oldest mailbox counters be forgotten. No practical gain for an attacker (they would have to send those 5,000 mails first); revisit if the ceiling is raised.
- **RR-I10 (C-L2 residue).** The loader pass is memoised per body (`cleanBody`, bounded at 2,000,000 characters, cleared when full), but `SafeHtml` still sanitises once during server render and once in the browser (`SafeHtml.tsx:51`). Steady state is one uncached pass per request on the server, 10 to 40 ms for a real policy, about 115 ms for the 300 KB worst case. Accepted as is.
- **RR-I11 (lockfile, SU-I6).** `storefront/package-lock.json` is still modified in the working tree (11 lines of `"dev": true` removed from lightningcss binaries). Do not commit it from this machine; regenerate or discard it before any commit.
- **RR-I12 (C-I4 notes).** Closed in the code comment (`content-pages-html.ts:14-17`: 300,000-character cut and unclosed drop-tags). The same text must reach the content guide for the client; I did not check `docs/handover` for it.
