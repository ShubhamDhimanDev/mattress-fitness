## What is sound (verified in code and tests)

- **Gate before any load or call.** `runtime.ts:156-167` `track()` sends or queues only for entries with `active`, and `active` is set only by `sync()` from the consent snapshot (`:146-154`). `GA4` globals (`dataLayer`, `gtag`, `ga-disable-<id>`) and `fbq` are created inside `adapter.load()` (`ga4.ts:103-122`, `meta.ts:156-171`), which runs only after `activate()` and on idle (`runtime.ts:118-131`). In opt-in mode nothing is created, requested or stored before a decision. Hydrogen's `publish` still runs in the US default (Shopify's consent answer), but every event then hits an inactive entry and is dropped; only the latest `page_view` (already reduced to a safe URL) is held in memory, never sent (`runtime.ts:158`, `:126`). Tests `runtime.test.ts:85-119` cover it.
- **Hydrogen's own consent still applies.** Our `canTrack` override (`ConsentAnalytics.tsx:144-148`) only decides whether Hydrogen publishes to subscribers. Shopify's subscribers re-check Shopify's own consent (`hasAnalyticsConsent()` at Hydrogen `index.js:63-68`, used at `:377`), so accepting a Google category does not push Shopify analytics past Shopify's own answer.
- **Withdrawal.** `deactivate()` clears the queue, cancels a scheduled load, revokes a ready adapter, and a load in flight revokes on completion (`runtime.ts:133-144`, `:109-115`). GA4 sets `ga-disable-<id>`; Meta calls `consent revoke`. Re-grant does not load twice.
- **Tampered cookie or storage.** `parseStoredConsent` (`consent.ts:51-81`) accepts only exact version, two booleans, a finite date, not older than 180 days, not more than 1 day ahead, at most 200 characters; anything else is "no decision". The server never reads this cookie, so forging it changes only the forger's own browser.
- **Opt-in default and env parse.** `config.ts:40-42`: anything but `opt-out` (after trim and lower-casing) is opt-in. Ids are validated by anchored patterns (`config.ts:32-34`, GA4 `G-` + 4 to 16 letters or digits, Meta 6 to 20 digits), so a quote, space, `;`, `UA-` or `GTM-` value yields `null` and means no provider, no script, no CSP host.
- **Script loader.** `script-loader.ts:37` refuses any origin outside the two provider origins before an element exists (URL parsed, `https` only, so user-info and look-alike hosts fail; tests cover them). Only the id varies in the GA4 URL and it is `encodeURIComponent`-ed after validation (`ga4.ts:67-69`); the Meta URL is a constant. The id is also used as a global name and cookie suffix; both are safe given the pattern and `SAFE_COOKIE_NAME`.
- **CSP.** Hosts are added only per set id (`entry.server.tsx:35-48`, `:77-83`); with none set both policies are byte-for-byte unchanged (tested). The same `analyticsCsp` input feeds the enforced policy (`enforcedCspExtras`) and the report-only one, so the provider hosts have parity; the enforced `script-src` repeats Hydrogen's `default-src` fallback sources because naming `script-src` replaces the fallback (checked against Hydrogen's `createCSPHeader`: `scriptSrc` and `imgSrc` are not merged, `connectSrc` is, and the nonce is appended to a named `scriptSrc`). No `'unsafe-inline'`, `'unsafe-eval'` or bare `*` was introduced; the script is added with the page nonce.
- **PII in events.** The cart mapper reads named fields only (`hydrogen-events.ts:129-140`, `:210-245`); buyer email, phone and name are never read. No user id, hashed email or advanced matching exists anywhere in `app/lib/analytics/**` or `app/components/consent/**` (grep). Parameter names and values are allow-listed and pattern-filtered (`privacy.ts:15-58`); the regexes are linear, not backtracking-prone. Quiz events carry only counts, a size and a handle. Meta `autoConfig` is turned off before `init` (`meta.ts:160`).
- **Failure isolation (NFR-013).** `async` script, 10 s timeout, every outcome a typed result, adapter and failure-callback exceptions swallowed (`script-loader.ts`, `runtime.ts:73-79`, tests `:265-336`). The log line is `analytics.provider_failed` with provider and a fixed reason only (`ConsentAnalytics.tsx:67-68`); no shopper data.
- **XSS.** Banner and dialog text are static strings rendered by React; no HTML sink in the commit. `data-analytics-*` attributes are re-validated when read back (`hydrogen-events.ts:283-314`).
- **Consent record.** `mf_consent` holds two booleans, a version and a timestamp: no identifier, no PII. `SameSite=Lax`, `Secure` on https, not HttpOnly by design.

## Findings

### Medium

**M-1 (T-05, T-16): the page address, page title and referrer reach Google and Meta unsanitised; only one explicit parameter is cleaned.**
Evidence:
- `privacy.ts:94-118` (`sanitizePageLocation`) is applied only to the `page_location` parameter that `PageViewTracker` passes (`AnalyticsBridge.tsx:111-114`, `hydrogen-events.ts:148-153`, `privacy.ts:37-45`). ANALYTICS.md:78 ("Search words, filters, ZIP and other query strings stay out") and `privacy.ts:68-69` describe this as the address "we report".
- gtag.js adds the document location, the referrer and the document title to every hit on its own, and `ga4.ts:109-113` sets none of `page_location`, `page_referrer` or `page_title`. Only the one `page_view` event carries our override; `view_item`, `add_to_cart`, `begin_checkout`, `search`, and the automatic events (`first_visit`, `session_start`, `user_engagement`, and per GA4 Enhanced measurement `scroll`, outbound `click`, `file_download`, `form_start`, `form_submit`, `view_search_results` from `q`, `s`, `search`, `query`, `keyword`) go with the full URL. Google's help states `page_location` and `page_referrer` are collected automatically and that Enhanced measurement is on by default ("By default, all event types are enabled").
- Meta `PageView` is sent with empty params (`meta.ts:62`); there is no code-level way to override what the pixel reports as the page (not documented by Meta: its conversion-tracking page says nothing about the URL or limiting it). The pixel's known behaviour of sending the document location and referrer with each event is **UNVERIFIED here** (Meta's page is silent; confirm in Test Events / network inspection).
- Real values this puts at risk: `/search?q=<term>` (`search.tsx:39`), whose term is not subject to the email and digit filter on this path; the search page title is `Search: <term>` (`search.tsx:22-27`) and GA4 collects the title; the account order page title is `Order <name>` (`account.orders.$id.tsx:26`) and the path holds the order id (`/account/orders/<id>`); campaign tags and click ids and any other query value on any page (for example an email-marketing click token).
Impact: a shopper who types an email address, a phone number or a street address into the search box has it sent to Google (URL and title) and Meta (URL) even though `sanitizeSearchTerm` would have refused the same text in the `search` event; order numbers reach GA4 through the title. This defeats the T-05 control "no PII in URLs" and the stated guarantee in ANALYTICS.md:78 and `meta.ts:9`. Needs consent first, and the shopper chooses the text, so likelihood is low and severity moderate; the documentation claim is the larger problem.
Fix:
1. GA4: before `config`, `gtag('set', {page_location, page_referrer, page_title})` from the sanitiser (location via `sanitizePageLocation`, referrer reduced to origin or dropped, title replaced by a fixed section label on search and account paths), and repeat the `set` on each navigation before the `page_view`. Unverified that GA4 applies `set` values to its automatic events; confirm in DebugView before relying on it.
2. A single guard in `privacy.ts` ("is this page safe to report": no private path prefix, every query value passes `looksPersonal`, search-term pages only when the term passes `sanitizeSearchTerm`), applied in the runtime or both adapters so that **no event at all** (including Meta `PageView`) is sent from a page that fails it. This is the only control that covers Meta's `dl`.
3. Add `/track-order` and `/delivery` to the private list at `privacy.ts:81` and keep `/account`, `/discount`, `/checkout-steps`.
4. GA4 admin checklist for the client before go live (document in ANALYTICS.md "To go live"): turn off Enhanced measurement site search, form interactions and outbound clicks (or accept them knowingly), enable Data redaction for email addresses and add the query keys `q`, `login_hint`, `_kx` and any others the client's email tool adds, set event data retention to the shortest value the client accepts, keep Google signals off.
5. Correct ANALYTICS.md:78 and the comments in `privacy.ts` / `meta.ts` so they claim only what is enforced.

**M-2 (T-16, NFR-011): at this commit a shopper cannot withdraw consent.** `PrivacyChoicesButton.tsx` is defined but nothing renders it (grep of `app/` at HEAD: only `ConsentPreferences.tsx` text mentions the footer link, "from the Privacy choices link in the footer"). The banner disappears after a decision (`ConsentBanner.tsx:20`). ANALYTICS.md:44 and :122 admit the gap. The working tree has an uncommitted `SiteFooter.tsx` that adds the button (`SiteFooter.tsx:177-180`, with a new `footerPrivacyChoices.test.tsx`); I did not review or run it.
Impact: for a store with ids set, consent given once can only be undone by clearing site data; the dialog text promises a link that is not there. Inert while no id is set.
Fix: commit the footer change, then verify in a browser that the link is keyboard-reachable, opens the dialog with the current choices, and that saving "off" stops requests and expires cookies. Condition for setting any id on a public URL.

### Low

**L-1 (T-10): CSP wildcard decision (`hosts.ts:19-27`): accept `*.google-analytics.com`, narrow `*.google.com`; do not require GTM server-side now.**
Decision requested in ANALYTICS.md:92. Google's own list for "Analytics without Ads features" (read today) is script `https://www.googletagmanager.com`; img `https://www.googletagmanager.com` and `https://*.google-analytics.com`; connect those plus `https://*.google.com`. The page says nothing about regional endpoints, `strict-dynamic` or server-side tagging reducing the allow-list, so those points cannot be argued from it.
- `*.google-analytics.com` (img, connect): accept. Google-operated, analytics-only, no user-hosted content; regional collectors such as `region1.google-analytics.com` need it, and an exact host would not stop exfiltration to an attacker's own GA property anyway (`www.google-analytics.com/g/collect?tid=G-ATTACKER` is already allowed). Record as an accepted exception to SECURITY_HEADERS.md "never a wildcard host" (owner's written acceptance needed, not given by me).
- `*.google.com` (connect): narrow. This registrable domain serves user-controlled content (`script.google.com` web apps, `docs.google.com`, `sites.google.com`, forms), so it is a ready-made data sink for any future script injection, which is the case `connect-src` exists to limit. GA4 with Google signals and ad personalisation off should need at most `https://www.google.com` and, for Google's analytics UI hosts, `https://analytics.google.com` and `https://*.analytics.google.com`. I could not confirm which of these GA4 actually calls (no property, no browser). Start staging with `https://www.google.com https://analytics.google.com https://*.analytics.google.com`, load every template with a real id and the console open in report-only, and add only a host that is observed to be blocked. Update `csp.test.ts:96-103` (it locks the wildcard set) accordingly.
- GTM server-side or first-party mode: not required. It needs a hosted server container and a custom domain, helps ad blockers rather than CSP risk, and the client has no Ads account in scope. Revisit if Google Ads, Meta Conversions API or a larger tag estate arrives.
Also `script-src` is on `script-src`, while Google's guide uses `script-src-elem`; equivalent here because only `script-src` is set, but if `script-src-elem` is ever added, the provider hosts must go there too.

**L-2 (T-16, NFR-011): withdrawal does not clear the cookies it claims to in the common case.** `cookies.ts:15` expires `_ga`, `_ga_<id>`, `_fbp`, `_fbc` on the exact host and `.host` only. GA4 and the pixel set these on the registrable domain (for `www.shop.example` that is `.shop.example`), which is neither. The adapters do stop sending (`ga-disable-<id>`, `consent revoke`) and the scripts are not loaded on later visits without consent, so no data flows, but the identifiers stay in the browser and come back into use if consent is given again, and ANALYTICS.md:45 and the module header understate how common this is (any `www.` host).
Fix: expire on every parent suffix with two or more labels (`a.b.c` -> `a.b.c`, `.a.b.c`, `b.c`, `.b.c`); a suffix such as `co.uk` is simply refused by the browser. No public-suffix list needed. Alternative: set GA4 `cookie_domain` to the exact hostname so scope is known (this does not help cookies already set).

**L-3 (T-16): "Nothing is sent until you agree" is not accurate for the whole page.** `ConsentBanner.tsx:32`. Shopify's own sales-channel analytics (Hydrogen `ShopifyAnalytics`, `monorail-edge.shopifysvc.com`, Shopify's consent script from `cdn.shopify.com`) follows Shopify's customer-privacy region settings, not this banner; in the US default it can run before and after "Reject all". `withPrivacyBanner: false` (`root.tsx`, pre-existing) hides Shopify's own banner. Either word the banner and the policy precisely ("Google and Meta tools wait for you"), or decide with the client whether Shopify analytics should also wait (that needs a code change to `canTrack`). Ties to the privacy-policy list below.

**L-4 (T-10): the analytics scripts run on pages that show or collect personal data.** `/track-order` (order number and email form, then an order summary), `/account/*` (orders, addresses, profile), `/delivery` form (ZIP), `/checkout-steps`. A third-party script has the whole DOM there. Meta autoConfig is off and GA4 form events carry no field values, so nothing is scraped as built, but T-10 lists "no ZIP or email to scripts" as the control and the compromise case (a vendor file is mutable and SRI is impossible, see I-2) is worst here. Fix: same guard as M-1 item 2, but at load level for these prefixes: do not run events, and do not keep the script resident on them (or accept and record it). Medium if the client's priorities treat the account area as high sensitivity.

**L-5 (T-16): GPC handling is narrow.** `consent.ts:90-102`. GPC is read only while undecided and only in opt-out mode, only for marketing (`defaultChoice`); a stored choice always wins, including an "accept all" given before the browser started sending GPC, and GPC does not reduce what "Accept all" turns on in opt-in mode. For California and several other states GPC is a binding opt-out of sale or sharing, and the Meta pixel for ad measurement and offers (`ConsentPreferences.tsx:21-22`) is a likely "sharing" case. Whether it binds this client depends on thresholds the code cannot know. Recommendation for the client's counsel: honour GPC for `marketing` in both modes and over an older stored acceptance (show the switch off and say why), keep the decision in the legal review (Q-012).

**L-6 (T-16): a withdrawal in another tab is applied only if `localStorage` fires a `storage` event.** `ConsentAnalytics.tsx:134-139`, `consent-store.ts:144`. The cookie is the primary store and does not emit events. If localStorage is blocked, a second open tab keeps sending until it reloads. Fix: also `refresh()` on `visibilitychange` and `focus`.

**L-7 (Info to Low): the consent cookie is unsigned and unscoped to the host.** `consent.ts:127-138` (no `Domain`, host-only, good). A sibling subdomain that can set a parent-domain `mf_consent` could forge "accepted" (cookie tossing); host-only cookies on the same name are read first-match by `readCookieValue` (`:105-121`), so the order is browser-dependent. Impact is limited to turning on analytics for that shopper, so accept; revisit if the client runs untrusted subdomains.

### Info

**I-1 (config, doc).** `PUBLIC_CONSENT_MODE` is trimmed and case-insensitive (`config.ts:41`; test `config-consent.test.ts:31-32` expects `'OPT-OUT'` and `' opt-out '` to loosen), while `.env.example`, ANALYTICS.md:26 and the module header say "only the exact value". Safe either way; align the text, or make the compare exact.

**I-2 (T-10): no SRI.** Accepted. `gtag/js` and `fbevents.js` are mutable, unversioned files; a pinned hash breaks them on release. Compensating controls are in place (origin allow-list in the loader, per-id CSP hosts, consent and idle gating, nonce). Residual risk stays on T-10: a compromise at Google or Meta runs with page privileges. SECURITY_HEADERS.md "Third-party allow-list policy" item 3 says "SRI where the vendor publishes a stable file"; neither does, so the rule is met by its own wording.

**I-3 (T-10): Meta host list is unverified** (`hosts.ts:9-11`; Meta's documentation is silent on CSP, re-checked today). Failure mode is lost data, not exposure: the enforced policy has no `frame-src`, so a Meta frame (for example for its attribution features) falls back to `default-src` and is blocked by the enforced policy; the report-only variant (which has `frame-src 'none'`) would show it in the console. Verify with a real pixel in report-only on staging before promoting.

**I-4 (T-05): residual search-term risk.** Free text that passes (`mattress 90210`, `123 Main St`, `jane at example dot com`) is sent as `search_term` / `search_string`. Documented at ANALYTICS.md:79. Acceptable once M-1 is fixed, if the privacy policy tells shoppers that search words are shared.

**I-5: retention of campaign parameters.** `utm_*`, `gclid`, `fbclid` are kept in the explicit address (≤100 characters, `utm_*` also checked for email and long digits). `fbclid` becomes `_fbc` (first-party, marketing category). Retention at the provider is a property setting (GA4 event data retention) the client controls; record the chosen value in the privacy policy.

**I-6: `begin_checkout` beacon.** `transport_type: 'beacon'` for `begin_checkout` and `select_item` (`ga4.ts:61-63`) is gated like every other event; it is sent only after consent, from the click on the `/checkout-steps` link, with cart lines only (no buyer fields). No cross-domain linker is configured, so no client id is appended to the checkout URL (good for privacy; GA4 sessions end at checkout, which is a reporting limit).

**I-7: dev-only `console.debug('[track]', ...)`** (`analytics.ts:76`) is behind `import.meta.env.DEV` and is removed from production builds. Parameters can include the reduced address; no redaction needed, but keep it dev-only.

## Privacy policy implications (T-16, for the client's counsel)

The page `/policies/privacy-policy` (linked from the banner) must exist and match practice before any id is set. At minimum it should say:
- Who: Google LLC (Analytics) and Meta Platforms, Inc. (pixel), plus Shopify (store platform and its own analytics), Extend (receives order data by design), the carrier or fulfilment apps; that Google and Meta act on the retailer's behalf for measurement and, for Meta, may use data for ad delivery (decide service-provider versus third-party and "sharing").
- What: IP address and device and browser data, page addresses and titles, referrer, the products viewed, added and checked out with prices, search words, campaign tags and click ids, quiz outcome size and top result handle (no answers), cookie identifiers `_ga`, `_ga_<id>`, `_fbp`, `_fbc`.
- Why and how long: measurement and advertising performance; provider retention settings; `mf_consent` lasts 180 days.
- Choices: the footer "Privacy choices" link (needs M-2), Global Privacy Control, how to clear cookies; in the states that require it, a "Do Not Sell or Share My Personal Information" or "Your Privacy Choices" link and a notice at collection; Shopify's own settings (L-3).
- That the delivery ZIP the shopper asks us to remember is stored in a cookie and is not sent to analytics; that no account data, email or phone is sent.
The opt-in default is the safe default; moving to `opt-out` is the client's legal decision (Q-012) and must be a written one.
